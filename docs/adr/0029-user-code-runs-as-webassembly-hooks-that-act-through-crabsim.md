# User code runs as WebAssembly hooks that act on the run only through crabsim

A user, or an agent they ask, can attach code to the model: hooks on every object that holds an MU (on entry, on exit and distribution), and before and after Init and Reset. The code is a WebAssembly module in the models folder's `code/` folder, compiled by the user from Rust to start with, or from any language that compiles to WebAssembly, and run by wasmtime in a sandbox: no files, network, clock or randomness of its own, a fuel cap per call, a memory cap. It reads any value of the run by its address, such as `Station 1.process_time`, and changes the run only by calling crabsim's actions, such as moving an MU, which crabsim checks and carries out with its own code, or refuses and says why. The engine knows only a trait for hooks, and wasmtime lives in a crate of its own. We decided it with the owner on 2026-11-26 in a design round of six rounds ([spec issue 156](https://github.com/MarcHoff94/crabsim/issues/156)), because real lines distribute and control MUs in too many ways to build in, and the owner wants users to write that logic themselves, from inside the model, without it being able to harm crabsim or the user's PC.

## Considered Options

- **More built-in strategies.** Declarative, so `validate_model`, the Paths view and `query_model` can read them, which is why round robin, weighted and by destination stay as the defaults. But each real line's control logic would need its own, and crabsim would never have them all.
- **A compiled Rust plugin, a DLL.** The fastest, a few nanoseconds a call. But it can crash the window, read any file, keep state crabsim can't copy into a checkpoint, and nothing holds it to being deterministic. Code an agent writes would run with the user's rights.
- **An embedded script language, such as Rhai or Lua.** No toolchain, editable in the window. But a call costs microseconds, 10 to 30 events' worth, on the per-MU path, and it is a second language to learn.
- **A language of crabsim's own.** The owner's wish since 2026-11-20, and the largest job by far. It could later compile to the same WebAssembly, so it isn't ruled out.
- **WebAssembly,** chosen: sandboxed, deterministic when given no clock or randomness of its own, its memory a plain block that a checkpoint can copy, compiled from Rust, C, C++, Zig, Go (TinyGo) and C#, and an expected call cost near one event, not measured yet.
- **A narrow, stable view for code.** Engine changes would never break user code, but the owner wants code to read the run's state and change other objects: it may break when the engine changes, and that is the user's responsibility. What is exposed is defined clearly instead.
- **Hooks called inside one another.** An action setting off another object's hook at once could recurse without end. Instead each hook runs alone, and the hooks it sets off follow it at the same time, in order.

## Consequences

- **Objects without hooks pay one check** of a boxed `Option` at each entry, exit and distribution, which must stay within ±2% on every benchmark scenario. A trigger point at an MU's rear needs an event the engine doesn't have today, scheduled only for MUs whose hook asks for it.
- **Results stay reproducible.** The code has no source of time or randomness but crabsim's: random numbers come from the deciding object's own stream. A hook runs at the time of its event, the hooks it sets off follow in a fixed order, and `ZERO_TIME_EVENT_LIMIT` ends a loop of them with a run error. One module instance lives for the run, its memory cleared at Reset and copied into every checkpoint, so going back stays exact. The hook before Reset may only read and log.
- **crabsim's state changes only through crabsim's code.** A move made by code runs the same engine code as one the engine makes: the MU leaves its object, whose queued events for it go stale, statistics and waiting predecessors are kept up to date, and the target takes it in. Only an MU in the middle of a handover can't be moved, since a transfer once begun always finishes (ADR 0023).
- **Reads cross the boundary as copies.** A list, such as a Buffer's contents, is a copy in the code's own language when asked for, so changing it changes nothing, and long lists are read through a handle one item at a time. A value changes only through an explicit setter, which crabsim may refuse. Addresses become handles when a module loads at Init, so a misspelled name is a problem before the run.
- **The engine stays free of WebAssembly** (ADR 0009). wasmtime is a dependency of the crate that hosts modules, which the model, the CLI, the catalogue and the window use.
- **Analysis can't see inside code.** `validate_model`, the Paths view and `query_model` treat a code distribution as able to send an MU to any successor, and say so. A better analysis needs the code's source.
- **A run records what code it ran:** the hash of each module, and on every occurrence from code a reference to its module, function and, with debug info, the source file and line.
- **Code's cost is measured apart** from results and from the engine's own: calls, fuel and wall time per function and object, in a `performance` table of the results store, never in `statistics`.
- **Debugging** is native for Rust: the same hook code compiled against the engine and debugged in the user's own `cargo test`. Stepping through WebAssembly inside crabsim isn't reliable on Windows yet, and works on Linux and probably WSL.
- **User-defined attributes** come later, in a round of their own, as the way code keeps its own state in the model.
- This settles "How the code gets in" under "User code (not built)" in the handoff, and its user phase at Init and Reset becomes the hooks after crabsim's own Init and Reset.

## Amended on 2026-11-27, while building PR 2

- **A plain WebAssembly module with a hand-written interface, not a component under a WIT world.** wasmtime gives no access to a component instance's core memories, so a component couldn't be copied into a checkpoint, which this ADR requires for going back to stay exact. A plain module's memory is copied in microseconds. The interface is versioned all the same (version 1, `docs/design/code-interface.md`), written for Rust in the `crabsim-guest` crate, and a module of another version is a model problem. Other languages need bindings written by hand. The owner dropped the component model for good on 2026-11-27 after it was measured (`docs/design/performance-trade-offs.md`): a call 3 times as dear, each read from crabsim about 13 times, and a checkpoint through saving and restoring state slower above tiny states and blind to state its author forgets. Agents write the code (the owner's direction since that day), so bindings for many languages matter less than crabsim compiling Rust for them.
- **Addresses** are an instance's name given as a parameter of type object, resolved to its id when the model is built, so a misspelled name is a problem before the run, and attributes read through typed functions (`Object::process_time`, `Object::mus_held`), so they can't be misspelled. A name looked up while the run goes (`find`) is the code's own risk.
- **Randomness** comes from each object's own stream for code, from the run's seed and the object's stream, apart from the numbers the object draws itself, so code asking for random numbers changes none of the model's own.
