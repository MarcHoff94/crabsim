# Agents model to expectations the user agreed, which crabsim checks itself

A user tells an agent what they want, such as "distribute everything from cross conveyor X between Stations A and B by how busy each has been", and cares about the result, not the code. So the agent first agrees with the user what the model must achieve, as **expectations** crabsim can judge on its own, tied to the user's **request**. Then it builds, with **rules** where they can say it and **user code** (ADR 0029) where they can't, and crabsim tells both of them whether the expectations are met. A model is **verified** once a deterministic run meets its own expectations, and **validated** once runs with randomness meet **reference figures** from the real line. We decided it with the owner on 2026-11-27 in a design round of five rounds, after PR 2 of spec issue 156, and specified in [spec issue 162](https://github.com/MarcHoff94/crabsim/issues/162). The owner's reason: code will be written by agents, not by hand, so crabsim should be built for agents writing, testing and proving it. Checks that crabsim runs without an agent cost the user no tokens.

## Considered Options

- **Agents check their own work.** An agent runs experiments and reads the results. But every check costs tokens, nothing survives the session, and an agent can declare success on a lucky run or by moving the goalposts.
- **Expectations the agent alone writes.** Cheaper to start. But the user would have to trust what the agent decided "done" means. Agreeing them first, and the agent being unable to change an accepted one, makes the user the one who defines the solution space, as in constraint programming. The agent may still question one, with its reason.
- **One judgement per run.** Simple, but a random run meets a limit by luck. Over an experiment, a verdict uses the 95% interval and may be "undecided, run more".
- **A second model without randomness for verification.** Error-prone. Instead a run option, deterministic, turns failures off and takes every random time at its mean, on the same model.
- **Code for every decision.** Code can't be read by `validate_model`, the Paths view or `query_model`, and needs a compiler. A rule's when/then lines cover the common decisions and stay readable and checkable. Code remains for the rest.
- **An expression language for rules and expectations.** The start of a second programming language. Text lines in a fixed form, parsed by crabsim, are enough, and an agent writes and corrects them reliably from exact error positions.
- **JSON objects for expectations and rules.** Unambiguous, but long, and harder for an agent to write than one line in the style of crabsim's command language.
- **The component model for code (ADR 0029, amended).** Bindings in many languages for free. Dropped: an agent writes Rust as easily as anything, and crabsim compiling it for the agent matters more.

## Consequences

- **Requests and expectations live in the model file,** changed through `edit_model`, undone with undo, shown in validation, so a model handed on keeps what it is for. A request holds the user's words, the agent's restatement, its expectations and its state. The changes and runs it refers to are linked by id. Accepting is the user's alone for now. A reviewer agent with its own role, never the one editing the model, is a later round.
- **An expectation's record maps onto SysML v2's requirements:** an id, its text, a subject (an object, a class with `every` or `mean`, or the model), a figure, a comparison and a value with an explicit unit, its stage, assumptions and its source. Its verdicts, met, not met, undecided or error, match SysML's VerdictKind. An import of SysML v2 text is a later feature that maps onto them.
- **crabsim keeps a model's stage,** draft, verified or validated, and drops it back when a change breaks a check, saying "not checked since change N". Verification runs when an agent or the user asks, and by itself when an agent releases its claim, when the window opens the model and before an experiment. Validation runs only on request.
- **One vocabulary of figures** for rules, expectations and code: everything crabsim measures, now, since start or over the last stretch, each with its meaning and unit. A stretch is kept in fixed buckets, and only for figures something names, so models without them pay nothing and memory stays flat.
- **crabsim compiles code itself,** with a pinned Rust it installs once per user, by the user's consent. It writes the crate's manifest: `crabsim-guest` alone, no build scripts, offline. The user may allow more, at their own risk. Code's sources are changed only through operations, with claims, history and undo, like model files.
- **Bounds crabsim can work out without running** warn of expectations that can't be met, such as a throughput above what a Station's process time allows.
- **A decision record,** an opt-in recording, says for each decision by a rule or code which figures it read and what it answered. Off by default, so headless runs stay flat.
- **One status operation and one panel** give an agent starting a session, and the user, the stage, the requests, the verdicts, what's questioned and the next step. The process is described in the MCP instructions for now; agent files or skills may take it over.
- **Agents get the CLI too,** with `crabsim operations`, `crabsim call` and `--agent <name>`, as an agent with the identity MCP gives.
- **Performance:** expectations, stages and requests are outside the run. Limits during a run cost one comparison where their figure changes, and stretches one bucket update, only for what is named. Rules cost their lines per decision, only where set.

## Amended on 2026-11-27, while building PR 1

- **The figures are the results store's names,** such as `working_share` rather than the design round's `busy_share`, so one figure has one name wherever it is read: an expectation, `query_results`, `compare_runs`, the Paths view. The store's figures are now built on the vocabulary (`crabsim::figures`), and store exactly what they did.
- **A limit costs the run nothing,** rather than one comparison where its figure changes: the statistics already keep the extremes a limit compares with (the most MUs held, the longest and shortest lead time), so whether a limit was broken is known at the end. Only an observation that broke one runs again, with its seed, recording MUs coming and going until it finds the moment and the MU. So limits are upper on the MUs held, which the statistics keep, and either way on a Drain's lead time; the fewest MUs held is `min_mus since start`.
- **`last <time>` at a run's end needs no buckets:** the run stops where the stretch begins, keeps that state, and the stretch is the difference of the two states' statistics, which add up. The buckets the design names come with rules, which read a stretch during the run. Figures that don't add up, such as the most MUs held or a median, are read only since start.
- **The scope is written every time,** as the subject's `every` or `mean` and the value's unit are: an agent never has to know a default.
- **`=` and `!=` are judged observation by observation,** as a state is: an interval says little about equality. Met when every observation holds, not met when none does, otherwise undecided.
- **Deterministic runs** leave out every failure profile, the only random times the engine has today. A warning for a verification check resting on code that calls `random()` waits for crabsim to know which hooks call it.

## Amended on 2026-11-28, while building PR 2

- **A check never changes the model file.** The stage, and whether a request is met or broken, are worked out from the checks the results store keeps (`runs.stage`, tables version 9), never written into the file, so a check changes no hash, no history and nobody's claim. The file holds only what people and agents set: an expectation's state (proposed, accepted, questioned with its question) and a request's `accepted` and `state`, `open` or `built`. A built request is met when every expectation of it was met in its latest check of the model as it is, broken when one wasn't, and built until then.
- **No stage rests on a proposed expectation.** Proposed ones are judged and shown, but verified and validated count only what the user accepted, so an agent can't reach a stage on goals it wrote itself. A questioned expectation stays in force until the user answers it, by accepting it again, changing it or removing it, so questioning one doesn't take it out of the stage either.
- **The user's own expectations are accepted at once.** What the user writes or changes, the user agrees with. What an agent adds is proposed. A request is always added unaccepted, and accepting it accepts every expectation it lists, in one step.
- **The user accepts past an agent's claim.** An agent holding the file waits for the user's acceptance, so a batch of only acceptances goes through its claim, which it keeps, rereading the model once, as after a take-over.
- **Every way to change a file is guarded,** not only `edit_model`: writing it whole, adopting it after an outside change, deleting it, and undo and redo all compare the file before and after and refuse an agent with `agreed` if the change touches what the user accepted. Renaming what an accepted expectation names keeps it: an instance is the same when it keeps its stream (ADR 0012).
- **A stage's check is one run for each set of settings,** the stage's own or an expectation's, each judging only its expectations. A check of the file as it is now that is done or going is given again rather than run twice. "Not checked since change N" names the oldest change still in effect after the one the check saw.
- **An agent through the CLI is known by its name,** `--agent <name>`, rather than by a process, since every `crabsim call` is a process of its own: its claims, its own changes for undo and its macros carry on from one command to the next, and it lasts while it keeps asking within the edit timeout, or while blocked. A `crabsim call` waits for the runs it started before it exits, since a run lives in the process that started it, and prints its output, or its error, as JSON.

## Amended on 2026-11-28, while building PR 3

- **Rules are a distribution strategy,** `{"rules": [...], "default": ...}`, as code's is, inherited as a whole: a Source, Station, Buffer, Conveyor or cross conveyor reads its lines in order as it passes an MU on, and its `default`, round robin, weighted or by destination, decides when no line holds or one says `default`. In the engine they are one more `Distributing` kind beside code's, on the same cold path, so a model without rules pays one comparison it already paid.
- **A line is `when <conditions> then <action>`, or `otherwise <action>`,** with `and` binding before `or` and no brackets. The conditions are the MU's class (a class standing for those derived from it) and next destination, the time of day from the run's start, another object's state now, and a figure compared with a value or another figure in the same unit, written as an expectation writes a figure. The actions are a named successor, waited for alone; the smallest or largest figure among some successors or all, `among those free` by default or `and wait`; `round robin` among some; `weighted among` some, by the object's own weighted ranking; and `default`. A rule never reads the object deciding: its figures are its successors' and other objects'.
- **A rule reads the statistics as they stand,** never a full state: the figures it can read are those the statistics keep as the run goes (`crabsim::rules::readable`), so a median or a fewest, which need the fill histogram, are left to expectations, and a stop by hand reads as failed, as the statistics count it.
- **A stretch is 60 buckets,** as the design said, kept only for what a rule reads over one, by the rules that read it: the statistics of the object read at each boundary, a bucket's width apart from time 0, read up to one bucket longer than its length, or since statistics began while the run is younger. The run rolls them before an event that reaches the next boundary, while the object's state is still what it was since its last change, so each is exact. Keeping them in the statistics keeper instead cost every model: a check on each change of state about 1.3% of instructions, and the keeper's changed layout about 4% of the demo's wall time even without it, so the keeper is as before and a model without rules pays one comparison an event.
- **On entry, setting an MU's process time from its class or a table, isn't built yet:** a work plan's steps already give an MU class its own process time at a Station, and a table by class is left for a later PR.

## Amended on 2026-11-28, while building PR 4

- **A reference figure is an `=` line with a tolerance,** `Drain.throughput_per_hour since start = 4100/d ± 3%`, at the validation stage with its `source`: the tolerance in the figure's own unit, or for a figure not counted in shares a percentage of the value, so `70% ± 5%` is 65% to 75% and `4100/d ± 3%` is 3977 to 4223 a day, as people read them. It is judged like any expectation by the 95% interval: met once the interval lies within the tolerance, not met once wholly outside it, undecided otherwise, with the observations that would decide it. `validate_model` warns of a validation expectation with `=` and no tolerance, which only that exact value meets, and of a reference figure without a source. Nothing else marks a reference figure: it is an expectation like the others, so verdicts, requests, stages and agreeing need nothing new.
- **Event logs are designed for, not built:** a log from the line's MES or SCADA, MUs entering and leaving objects with their times, is what a run records as occurrences, so crabsim will read the same figures from one as from a run's states, and a reference figure will take its value from a log over a period instead of a typed number, its `source` naming the log. Fitting process times or failures from logs stays later.
- **A bound is certain, never a guess, with one exception.** crabsim warns that an expectation can't be met only when the model alone proves it: a figure's range, capacities, what never happens in a check (a failure at the verification stage or of an object without a profile, a pause, receiving without a conveyor leading in), a maximum flow for MUs in and out, throughput and a Station's busy share, the shortest way's work for lead times, and contradictions between expectations of the same figure in the same check, or shares of time that can't add up to 100%. A guess would teach agents to ignore the warning. The exception is a since-start throughput, which counts the MUs after the Drain's first over the time since it, so MUs coming together just before the end could make it anything: it is bounded as if the first came as early as it can, which held in every run of the model files tried, and a run whose first MU comes much later, such as one starved at its start, could beat it. An object in a loop is bounded by its own pace alone; a model with code only by range, capacity and contradictions, since code can move MUs and change times.
- **Bounds are warnings, never verdicts:** they are `validate_model`'s warnings at the line and `get_status`'s `cannot_be_met`, worked out on request outside any run, and the next step, ahead of checking, tells an agent to change the model or a proposed one before the user accepts it, and to change the model or question an accepted one: can't be met means as the model is. A check still runs and judges it.
- **Setting an MU's process time on entry,** left out of PR 3, and the Paths view showing which successors a rule prefers, stay for a later PR.

## Amended on 2026-11-28, in a design round after PR 4

The design's "on entry, a rule may set the MU's process time from its class or a table", which PR 3 left out, settled with the owner in seven rounds, together with expectations on which MUs an object may take. Work plans stay as they are (ADR 0026, amended the same day).

- **A Station's time by MU is rule lines in its `process_time`:** `{"rules": ["when class = Frame then 30s", "when step = Deburr then 50s"], "default": "20"}`, a plain time staying valid. A line's action is a time or `default`. Its conditions are the distribution rules' (an MU's class, the time of day, another object's state, a figure), without the next destination, and with `step = <class or instance>`, the MU's current step, which distribution rules gain too. A table by MU class is the simplest set of lines, so it needs no form of its own.
- **The default is the Station's own time:** what an intervention changes, Keep changes saves, weighted distribution and the Paths view weigh, and what applies when no line holds. The whole is inherited as one value, as a distribution is.
- **A plan step's own time wins** when the MU is on plan at the Station, so today's models keep their results; the lines decide for MUs off plan, without a plan, or on a step without a time. Considered and dropped: the lines winning, and refusing both at one Station.
- **Stations only, decided at entry,** before a Station with capacity in batch mode waits for its batch, as the design said. A Buffer's dwelling time, a Source's interval and a cross conveyor's switch time could take the same form later. The bounds take the smallest and largest time the lines can give, with the default and plan steps. The window gets a Rules box for it; the command language takes lines later, as for distribution rules.
- **An MU's current step,** read as `step` by expectations and process-time lines at entry and by distribution rules as the object passes the MU on: while the MU has a detour, from getting it until it reaches it, what the detour names; otherwise what its plan's current step names; none without a plan or past its last step. A step is known by the class or instance it names, not by its place in the plan, which shifts when steps are inserted, nor by a name of its own: products visit an object at different stages of their plans, and what a step names is already checked. A listed class stands for the classes derived from it and their instances, a listed instance for itself alone.
- **Which MUs an object may take,** a limit on any object MUs enter, `every` allowed: `Mill.step always in Welding, Deburr` and `Press.class always in Frame, Door`, with `not in` for the reverse. A listed name that is no class or instance is a problem. An MU without a step breaks a `step` line. It is a check, never a constraint: refusing MUs is routing, which distribution by destination and rules already do.
- **Such a limit costs one check at entry where an expectation names the object,** as the design first said of limits, folded into the check every entry already makes for recording and hooks, so a model without one pays nothing, measured within ±2% on every scenario. A run is told which objects to watch: stage checks, experiments and the CLI's headless run, which judge expectations, and not the window's live session. An observation's value is the number of MUs that broke it, not met when any did, the verdict naming the first: when, at which object, the MU, its class and its step. No bounds for these: whether an MU reaches an object depends on routing.
- **Order:** spec issue 162's next PR, ahead of the decision record, which then records process-time lines' decisions too. A detour that is a small work plan slotted into an MU's plan during a run, such as inspection sending a failed weld back to welding, is a design round of its own next (ADR 0026, amended).

## Amended on 2026-11-28, while building PR 5

- **Lines reading other objects need no restriction:** whoever hands an MU to a Station with time rules works out its time as the MU enters (`enter_deciding_time`), reading the others and itself, since a Station can't reach the other objects as it takes an MU. The giver reads as it stands at that moment, having counted the MU out. So every condition the design named works, and no zero-time event of the Station's own was needed. A model without time rules pays one check at each move.
- **The time rules live in the run's event context, not the Station,** which is handed the decided time as the MU enters: a box on every Station grew every object in a run from 592 to 600 bytes, since every object takes the size of the largest, which the 6,006-object scenario would have paid for.
- **`default` is required** in a process time by rules, the Station's own time, so a line's `default` never means something an agent must look up. A line's time is written with its unit (`30s`, `1:30`), a bare number a problem, as in expectations. Starting MUs, which never enter, take the Station's own time.
- **`step` reads the same destination as `next_destination`** (its detour, else its plan's current step), but matches by what a listed name stands for: a class, itself, the classes derived from it and their instances; an instance, itself alone. A run knows destinations standing for the same objects as one, so a listed instance also matches a step naming a class whose only instance it is.
- **A limit on which MUs an object takes needs no replay:** the run counts the MUs that broke it and keeps the first as they enter (`crabsim::watch`, `RunState::watches`), so its value is that count and its violation comes from the run's state, `none` for an MU without a step. The results store's `violations` gain `class` and `step`, tables version 10.
- **An MU class alike another in every value gets an MU kind of its own** once a Source makes it: before, such a class shared the first one's kind, so a rule's `class = Tote` never held for a Tote the size of the built-in MU, and a limit couldn't tell them apart. Models whose MU classes all differ keep their kinds' ids; `models/conveyor-line.json`, whose Tote is the built-in MU's size, now records its MUs as a kind of their own, with every result the same.
