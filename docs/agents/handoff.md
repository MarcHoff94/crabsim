# crabsim handoff

Written 2026-11-07 at the end of a working session, and updated after each step since, last on 2026-11-28 after PR 5 of spec issue 162, process times by MU and which MUs an object takes, was built in a cloud session and merged as #170. Read this first, then check it against the code and git, because it describes a moment in time.

**The UI's order of work is done.** UI stage 1 was built in four slices, PRs 24 to 27: the demo drawn live with state colours and MUs, pan and zoom, the run controls, speed, time mode, stepping, going back to a time, the error banner, the inspector, interventions on Stations and their marks. Step 7 trimmed the CLI to a headless run of the demo, in PR 30.

**The model file is complete.** Issue 28's steps 1 and 2 are merged: the `SessionOutput` rename (PR 33), and the model file in three slices (PRs 34 to 36): `crabsim-model` reads, checks and saves model files with classes and inheritance, `models/demo.json` is the demo as a file, the CLI runs model files from `cli/` (ADR 0009), and `models/model-file.schema.json` is the published schema. The design is in `docs/design/model-file.md`.

**The operation catalogue is built through slice 3,** with the MCP server and the CLI as its front-ends, 25 tools over MCP since `find_bottleneck` (PR 85). The design is in `docs/design/operation-catalogue.md`.
- **Slice 1, MCP v1** ([spec issue 37](https://github.com/MarcHoff94/crabsim/issues/37), PRs 39 to 42): model file operations, the SQLite results store (ADR 0010), runs as jobs, results, the CLI's subcommands and the MCP server, and runs marked interrupted when their process ends first.
- **Slice 2** ([spec issue 45](https://github.com/MarcHoff94/crabsim/issues/45), PRs 47 to 52): `edit_model` and `get_attributes`, an editor per model file with an edit queue the user controls (ADR 0011), changes from outside detected and adopted, and the first harness trial's fixes. - **Slice 3** ([spec issue 56](https://github.com/MarcHoff94/crabsim/issues/56), PRs 59 to 61): `describe_model`, `query_model` with seven kinds of graph question, `export_model` into `exports/`, and the CLI's `describe`, `graph` and `export`.

**UI stage 2 is done** ([spec issue 63](https://github.com/MarcHoff94/crabsim/issues/63), PRs 65 to 70): the window works on a models folder through the catalogue as the user, lists and runs its model files, picks up an agent's changes, shows and changes every attribute of an instance in the inspector, and has an Editing tab with the user's control of the edit queue. Both front-ends now always work on a model file: the built-in demo is gone from them. See "UI stage 2 (built)".

**Claims are done** ([spec issue 73](https://github.com/MarcHoff94/crabsim/issues/73), ADR 0013, PRs 75 to 77): an agent claims a model file with its goal and what it's doing, is refused if someone holds it, and the user sees and manages the claims in the Editing tab, the CLI's `crabsim editors` and a marker on the open model. Trial 3 tried it with a Claude Code agent on 2026-11-09, and PR 77 fixed what it found.

**The first-time experience is done** ([spec issue 78](https://github.com/MarcHoff94/crabsim/issues/78), PRs 79 to 85): a walkthrough as a newcomer found twelve stumbling blocks (`docs/design/first-time-review.md`), and the owner decided eleven of them in a grilling session. The window starts with no arguments on `Documents\crabsim-models` holding the demo, lists only model files, explains every control and state, can race as fast as a headless run with Animate off and go to any time, keeps or names changes on Reset, and has a Results tab with the likely bottleneck, by one rule that `find_bottleneck` gives agents too. See "First-time experience (built)".

**Undo, [spec issue 107](https://github.com/MarcHoff94/crabsim/issues/107),** designed with the owner on 2026-11-13 in three rounds (ADR 0017): one change history per model file in `.crabsim/history.sqlite`, with everyone's changes, each storing the file's whole text, so undo and redo write a text back exactly. This was done on the owner's second PC, where `gh` is installed since that day and nothing else from "Folders outside the repository" or "Installed binaries" below exists.

**Build step 7, the domain model, is designed in its first round, [spec issue 110](https://github.com/MarcHoff94/crabsim/issues/110),** with the owner on 2026-11-13 and 2026-11-15 in four rounds: Buffer made to work, Station capacity, and blocked predecessors waiting by MU. **Its PR 1 is merged** (PR 111, 2026-11-17), and so is an allocation fix found by measuring it (PR 112): waiting by MU (ADR 0018), Buffer with a capacity or none (ADR 0019), a dwelling time, both exit strategies and starting MUs, the Source fix, and Buffer in the model file, the catalogue and the window. **PR 2, Station capacity, is built** on the branch `feat/station-capacity`: a capacity and a start (individual or batch) on a Station, busy time split into full, not full and partly blocked, and the likely-bottleneck rule counting only busy and full. **Build step 7's second round is done, [spec issue 122](https://github.com/MarcHoff94/crabsim/issues/122), closed,** with the owner on 2026-11-20 in four rounds (ADR 0020): every object type can be interrupted through one struct, `Interruptions`, and a thin trait, `Interruptible`, replacing `StopCtrl`; the combined state is renamed Interrupted and forced failure Stopped; an object has several named failure profiles, each with its own stream; profiles count on a time basis; and a stopped predecessor keeps its place in line. **Conveyors are designed, [spec issue 133](https://github.com/MarcHoff94/crabsim/issues/133),** with the owner on 2026-11-21 in a grilling session of four rounds (ADR 0021 to ADR 0024, amendments to ADR 0004 and ADR 0008, and the Conveyors section of `GLOSSARY.md`): MU classes with a footprint, conveyors that are geometry-aware objects, a booking point deciding every transfer, motion as closed-form plans rather than time steps, and paths as chains of segments. See "Conveyors (spec issue 133)" under "Agreed design" and `docs/design/conveyor.md`.

**User code is designed, [spec issue 156](https://github.com/MarcHoff94/crabsim/issues/156),** with the owner on 2026-11-26 in a grilling session of six rounds (ADR 0029 and the glossary's User code section). The owner asked for the round in place of conveyors' increment 4. It began as user code for distribution and grew into user code in general: hooks on every object that holds an MU (on entry, on exit and distribution, each at an MU's front, booking point or rear) and before and after Init and Reset, running functions from WebAssembly modules the user compiles into `code/`, in wasmtime's sandbox with fuel and memory caps. Code reads the run by address (`Station 1.process_time`) and changes it only through actions crabsim checks and carries out, moving an MU whatever its state among them. A distribution answers one successor (waited for alone), hold, or default. Performance of code and engine is kept apart from results, in a `performance` table and a Performance window of its own OS window; log lines and actions carry a reference to source; Rust hooks debug natively; the window gets breakpoints on hooks and a log window. Four PRs, none built: the engine with hooks in Rust tests, WebAssembly, the catalogue, the window. User-defined attributes are a round of their own after PR 2. Decided while writing it up: `Address` rather than `Path` for `Object.attribute`, since Path is a conveyor's line. **PR 1a is merged** (#158, 2026-11-26), with models without hooks 4 to 8% slower, which the owner accepted for now: the owner split the spec's PR 1 into 1a, objects without geometry, and 1b, conveyors and cross conveyors with their Front and Rear trigger points, the rear event, moving MUs onto and off belts and moving a code distribution's moment; decided that on_exit runs as the MU actually leaves (distribution, the move, the old object's on_exit, the new object's on_entry), and that a held MU shows as Blocked. See "User code (PR 1a)" under "Agreed design". **PR 1b** is merged (#160, 2026-11-27). **PR 2, WebAssembly, is merged** (#161, 2026-11-27): a plain module rather than a component, for checkpoints; the owner dropped the component model after it was measured. See "User code (PR 2)".

**Agents model to agreed expectations is designed** (ADR 0030 and the glossary's "Agreeing and checking"), with the owner on 2026-11-27 in a grilling session of five rounds after PR 2. A design round after it settled process times by MU as rule lines in a Station's `process_time` and limits on which MUs an object takes (`Mill.step always in Welding, Deburr`, `Press.class always in Frame, Door`), to be built as #162's PR 5, ahead of the decision record (PR 6), and left detours as small work plans slotted in during a run for a round of its own. **PR 5 is merged** (#170, 2026-11-28, built in a cloud session): a Station's `process_time` as rule lines, `step` in rules and expectations, and limits on which MUs an object takes, watched in runs that judge expectations; along the way, MU classes alike in every value got MU kinds of their own, which fixed PR 3's `class = …` for them. **Next** is the decision record (PR 6), or the design round on detours as small work plans first. A guide for trying PRs 1 to 5 by hand, with one example model and the output each step gives, was written for the owner as a Claude doc, outside the repository. See also "Reference figures and bounds (PR 4, merged)", "Rules (PR 3, merged)", "Stages, requests and agreeing (PR 2, merged)" and "Agents model to agreed expectations (designed)" and "Expectations (PR 1, merged)" under "Agreed design".

## Agreed design

The owner decided all of this. Don't reopen it without a reason, and flag it if you need to. **Built** means it's in the code now, and **not built** means it's agreed for later.

### Performance (built where noted, otherwise not yet)
Performance is the first thing to weigh in design trade-offs. It is a guideline rather than a hard rule, and `CLAUDE.md` holds the wording and the measuring rules. The target scale is up to 6,000 objects (raised from "a few thousand" on 2026-11-07) and tens of simulated years per run, with no fixed speed target. The benchmark's large scenario is 6,006 objects (429 copies of the demo) since step 1 of the UI's order of work.

- **Headless run (built):** a plain simulation run with no live session or view, not a separate mode. It gives back its final state and the objects' data, with no reset, including after a run error.
- **Recording (built)** is a runtime setting on the run for which occurrence kinds to keep, changeable at any time, because replay needs it off and then back on. A run records nothing by default, and a live session records everything.
- **Results (built)** of fixed size come through `run.state()`, with `ObjectState` extended. Recorded occurrences come back from each advance (ADR 0004).
- **Statistics (built, for what today's model has)** are fixed-size, always on and independent of occurrences. See "Statistics" below.
- **Live session (built):** read-ahead with checkpoints and replay, on one thread that alternates between computing a slice and releasing what the clock has reached. See ADR 0002 for the mechanism and why.
  - **Buffer:** limited by a maximum number of instants, with no limit on how far ahead in time the run gets. When it's full the run waits and still handles commands.
  - **Time:** Halt, errors and everything else the user experiences follow shown time. Reset throws the buffer away. If computing falls behind the clock, shown time waits and carries on from there, with no debt. A panic while computing also waits for shown time to reach it.
  - **Time modes:** continuous, or skipping, where no gap between instants takes longer than a set wall time (0.25 s to start with). Switchable at any time, and results don't depend on it.
  - **Going back:** `go_back(to)` reaches any earlier instant, also out of a run error, and leaves the session halted with a full state. `step_forward()` shows one instant while halted, and `step_back()` goes to the instant before the one on screen. An instant is a time with occurrences.
  - **What the UI gets:** one full state at Init, after Reset and after a jump back, occurrences and `ShownTime` in between, and a full state on request, from a replay on a copy. `crabsim::Picture` rebuilds contents, process state, every active interruption and remaining time from them. Blocked predecessors and statistics come only from a full state.
- **Checkpoints (built):** kept up to a memory budget the user configures. When it is full, every other checkpoint in the older half goes and the one from Init stays, so the whole run stays reachable. Every 100,000 events, with 256 MB, to start with. A checkpoint is a clone of the run, plus how much of the intervention log is in it, and a test checks that restoring and replaying gives occurrences identical to the original run.
- **Interventions (built, on Stations only):** take effect immediately at shown time, without a Halt, and discard the computed future. Pause on and off, forced failure on and off, changing a process time, and clearing statistics for a warm-up. Same seed plus same intervention log gives the same result. There are no branching timelines. Reset can keep changed process times as the new default state, a session setting that is off by default.
- **Object storage (built):** one `Vec` indexed by id, successors stored as ids, an `enum` for the object type. See ADR 0005.
- **Threads:** each run executes on one thread at a time, and can move between threads. Cores are used through distributed simulation, which means many simulation runs at once, such as the observations of an experiment. One `ModelDescription` can already build many runs, but nothing else is built for this yet.
- **Time representation (built):** simulation time is a 64-bit count of milliseconds behind its own type, `SimTime`. Process times and sampled failure times are whole milliseconds, with sampled times rounded rather than cut off.

### Model
- **Material-flow objects** are Source, Station, Buffer, Drain and, since spec issue 133, Conveyor. Each handles MUs and represents a real thing. "Station" means only the processing type. This is a general simulator for any material flow, such as a factory line.
- **Every material-flow object can fail**, so all of them get `StopCtrl`, even ones that consume no time, like a Buffer. Each gets a failure profile, and availability 1.0 means it never fails. *Not built: only Station has failures, and `StopCtrl` is `todo!()` everywhere.*
- **Station capacity** replaces a separate ParallelStation (ADR 0001). It's one machine working on several MUs at once, **not several parallel machines**. Capacity 1 is the default. *Built in PR 2 of build step 7, for the rules below.*
  - **Start modes:** batch start (work begins when full) and individual start (each MU starts on entry).
  - **Partly filled batch start:** waits indefinitely, with the waiting MUs visible in state. A timeout can come later if needed.
  - **Batch entrance:** closed once full, until the Station is completely empty.
  - **Individual entrance:** open whenever a slot is free. A finished MU still waiting to leave occupies its slot.
- **Buffer** holds MUs and stays a separate concept from Station even though it can behave alike (ADR 0001). *Built in PR 1 of build step 7, without stops.*
  - **Dwelling time:** one fixed value per Buffer, default 0, counted individually from each MU's entry.
  - **Stops and dwelling time:** a stop doesn't affect dwelling time by default, and this is configurable.
  - **What a stopped Buffer does:** entrance and exit are closed, and it keeps its contents.

### Build step 7, round 1 (built: PRs 111, 113 and PR 3)

[Spec issue 110](https://github.com/MarcHoff94/crabsim/issues/110), decided with the owner on 2026-11-13 and 2026-11-15. It adds to and sharpens "Model" above. In short:

- **Scope:** Buffer, Station capacity and how blocked predecessors wait with several MUs per object, with the Source bug fixed on the way. Stops on Source, Buffer and Drain, `StopCtrl`, the failure time bases and whether a stopped predecessor keeps its place are the second round.
- **Waiting by MU:** a successor's line of blocked predecessors is ordered by how long each predecessor's next MU has been ready to leave. With one MU per object that is today's order. The owner chose it over a predecessor keeping its place until empty, which starves the others, and over taking turns per object.
- **Buffer:**
  - **Capacity** is a whole number from 1 or unlimited, and a new Buffer is unlimited. Written `"unlimited"`, with `-1` accepted wherever a capacity is entered and saved as `"unlimited"`. The owner wants unlimited knowingly: it grows only as far as it's filled, and is the one case where memory isn't flat. Validate warns, and nothing limits it.
  - **Exit strategy:** the Buffer decides which MU it shows to the movement code, which never knows the strategy, so strategies are added without touching it. First in, first out by default, and last in, first out, each among the MUs whose dwelling time is over. Stations with capacity keep "earliest finished first".
  - **Starting MUs** up to its capacity.
  - **States:** empty, holding and blocked, holding with its own word and colour.
- **Station capacity:**
  - **Starting MUs** up to its capacity. A full starting batch begins work at Init, and a part of one waits.
  - **States:** work outranks blocking, so it's blocked only when nothing is in work and a finished MU can't leave. A batch waiting to fill is idle.
  - **Busy splits into three parts that don't overlap,** the owner's idea for finding bottlenecks with capacity above 1: full, not full, and partly blocked (it works while a finished MU can't leave), which outranks the other two.
  - **The likely-bottleneck rule** counts only "busy, full" and stopped time.
- **Fill statistics for a Buffer,** asked for by the owner: mean, median, lowest and highest number of MUs and the full share, weighted by time, and a histogram of 64 bars. Its width is automatic by default (one level per bar up to 63 MUs, then doubling), or set with `histogram_bar_width` on the Buffer, where the last bar then collects everything beyond the range. A stored run keeps the figures and the histogram, the histogram in a table of its own.
- **During a run:** the rules are set (capacity at once and refused below the MUs held, the rest from the next MU or batch), and the interventions come with the live-session operations.
- **Model file:** `capacity` and `start` on a Station, and `capacity` (now optional), `dwelling_time`, `exit_strategy` and `histogram_bar_width` on a Buffer, all optional, so the format stays version 2.
- **Performance:** the benchmark's existing scenarios stay within about ±2% of the baseline on the second PC, with figures in each PR, and a new scenario with Buffers and a capacity Station is added. The demo stays as it is, and `models/buffered-line.json` is a second example.
- **Three PRs,** each tryable in the window: waiting by MU with Buffer and both ADRs, then Station capacity, then fill statistics.
- **PR 1, built on 2026-11-16, and what it settled beyond the spec:**
  - **Each place in a line has its own time.** A first version ordered the line by one "ready since" per predecessor, and the demo's hashes changed: a Station stopped while blocked keeps its old place where its retry wasn't used up, and rejoins at the back where it was. So a successor no longer empties its line when it sends retries: each entry stays, marked, until its retry is answered. Refused, the predecessor is back in its place, and otherwise the place is gone. With that, every occurrence of the demo and of two other models hashed the same as `master`.

  - **A stopped Station's MU** counts as ready again from the end of the stop, which is today's behaviour. Whether it should keep its place is still the second round's question.
  - **A last in, first out Buffer keeps its place** while it waits, though the MU it would pass on changes as newer ones become ready. Following the newest MU would send a stack to the back of every line each time one arrives.
  - **A Buffer's events:** one `MUExit` per MU at the end of its dwelling time, which is one event for an MU that enters a blocked Buffer and does nothing. Not optimised.

  - **The warning about an unlimited Buffer** compares MUs per hour in and out from the Sources and Stations directly beside it, and says nothing when anything else is beside it. A rough rule, the PR's own.
  - **A Buffer starts with at most 1,000,000 MUs,** a check the spec didn't have, so a typo can't take the memory at Init.

  - **Done in PR 3:** Buffers in the Results tab, the median and the histogram.

### Interruptions (spec issue 122, done)
[Spec issue 122](https://github.com/MarcHoff94/crabsim/issues/122) and ADR 0020, decided with the owner on 2026-11-20, change several points below. Where they differ, these win:
- **`Interruptions` and `Interruptible`:** a plain struct keeps the bookkeeping once (active interruptions, the most serious, the failure profiles and their clocks, `stop_count`, when it began), is handed each stop event and says what changed. Every type implements the thin trait `Interruptible` (`stop_began`, `stop_ended`). The cause is `Interruption` { `Failed`, `Stopped`, `Paused` }, replacing `StopCause` and `InterruptionState`. `StopCtrl` goes.
- **Names:** *Stop* is now **Interrupted**, and *forced failure* **Stopped**, in the glossary, the code, the operations (`interrupted`, `full_or_interrupted_share`) and the results store, whose columns a version bump renames.
- **All four types** get failures, Stopped and Paused. A Buffer's dwelling time keeps running while it's interrupted unless `stop_freezes_dwelling` is set, which freezes it: the MUs still dwelling become ready later by the interruption's length, each with a fresh exit, since the queued ones would come too early (the spec's "reschedules nothing" couldn't hold).
- **A stopped predecessor keeps its place in line,** with its MU's original ready time, skipped while it's interrupted. This changes results on purpose.
- **Failure profiles:** `failures` is a list of named profiles (`name`, `stream`, `availability`, `repair`, `time_basis`), independent of each other, each with its own stream and its own failed time and number of failures in the statistics and the results store. A single old `failures` object reads as a list of one named "Failures". Adding a profile to an instance that inherits its class's list copies that list first.
- **Time bases per profile:** simulation (default), working and processing on Stations and Sources, simulation and working on Buffers and Drains, checked lazily: a failure is scheduled at its earliest possible time and rescheduled for the rest if too little has counted when it fires.
- **Commands:** `add`, `remove` and `rename failure`, on one object, a comma-separated list or `$selected`, each object getting its own copy and stream.
- **Out of this round:** a shift calendar (Off shift would be another cause, counting like a pause), expressions picking objects in commands, merging profiles by name, and agents interrupting objects during a run (#28 step 7).
- **PR 1, built on 2026-11-20 on `feat/interruptions`, in three commits:** the move onto `Interruptions` (`src/materialflow_objects/interruptions.rs`) with occurrences and state hashed identical to `master` (the demo and the buffered line, plain and with every Station general, seeds 0, 7 and 123, 20 days, with and without pauses and stops by hand); the rename, under which every test checks what it did before; and a waiting predecessor keeping its place, which changes results on purpose (all but one of those hashes) and has its own test, failing under the old rule. What it settled beyond the spec: `stop_count` stays with each type, since only it knows whether a stop froze work, and the results store needed no change, having no column named after a stop (ADR 0020 corrected). The Station's failure profile is boxed in `Interruptions`, so every object shrank from 1,280 to 1,080 bytes, and the 6,006-object model's heap grew from 19.6 to 24.4 MB, the profiles now being allocations of their own. A model file's state note `forced_failure` is read as `stopped`. Trying it found the window still calling the combined state Stopped, now Interrupted, and an older fault, also on `master`: after a stop by hand is ended while the run is halted, Work left shows the completion time (00:03:25) rather than the time left (5 s).
- **PR 2, built on 2026-11-20 on `feat/interruptions-everywhere`:** Source, Buffer and Drain implement `Interruptible`. A Source's interval freezes and its queued exit is voided through `stop_count`. A Drain refuses MUs and sends retries when back. A Buffer takes and releases nothing; with `stop_freezes_dwelling` it bumps `stop_count` at the start, and at the end moves every MU still dwelling later by the length, each with a new exit. Each keeps its place in line while interrupted. `ModelDescription::set_failures` gives a Source, Buffer or Drain a failure profile, and a failure event for an object with none stays a run error (the run-error tests rely on it). The live session pauses and stops any object; only a process time is a Station's alone. In model files `failures` applies to every type, a Buffer has `stop_freezes_dwelling` (true or false), and every type's state notes cover Failed, Stopped and Paused. The window offers Pause and Stop on every object, shows a Source's, Buffer's or Drain's interruption figures once it has had some, explains each type's interrupted states, and has a "Dwelling in a stop" menu. What it settled beyond the spec: a Buffer's fill keeper is boxed, since the Buffer had become the largest object (1,128 bytes), so every object is now 584 bytes; and on the command line an attribute that begins with what was typed wins over others holding it, so `dwell` still means `dwelling_time` beside `stop_freezes_dwelling`. Models without these interruptions hash identical to `master`. Benchmark against PR 1, one run each: demo headless 8.60M against 8.81M events/s, 6,006 objects 4.83M against 4.78M, demo dropped 7.77M against 7.73M, buffered line 7.49M against 7.38M, with the 6,006-object heap down from 24.4 to 17.3 MB. - **Between PR 2 and PR 3, scheduling without a `Vec` per event (PR 126, merged 2026-11-21):** an object's event handler now returns `Result<(), RunTimeError>` and schedules what follows with `EventContext::schedule`, into one list the run moves into its queue after each event and hands back emptied. `Interruptible::stop_ended` and `retries_for_blocked` take the context instead of a list, and `Interruptions::handle` returns only the `Change`. Only `init` still returns a `Vec`, once per object. The order of `schedule` calls is the order of ties in the queue, so every handler keeps the order its list had: a Station schedules its retries before its successor's event when an MU leaves, but its successor's event first when a stop ends, and a Source its next MU's exit before its successor's event. - **PR 3, built on 2026-11-21 on `feat/failure-profiles`, merged as #128, several named failure profiles:** `Interruptions` holds a list of `FailureProfile`s, each with a name, an optional stream, and its own failures and failed time, boxed as `Option<Box<Vec<_>>>` so every object stays 584 bytes (a `Box<[_]>` is a fat pointer, 16 bytes, so the note below was wrong). `StartFailure(u8)` and `EndFailure(u8)` name the profile, keeping a queue entry at 32 bytes, and `InterruptionBegan` and `InterruptionEnded` carry `profile: Option<u8>`. Overlapping failures of two profiles are one Failed interruption, which keeps the time the first began and ends with the last; the `Picture` keeps which profiles are failing. `ObjectState::failure_profiles` reports those that can fail (100% available ones left out, so `index` can skip numbers), with `ModelDescription::set_failure_profiles`. What it settled beyond the spec:
  - **A profile's stream is its own within its object,** not a model-wide number like an instance's: seeded from the object's seed and the stream, the stream defaulting to its place in the list, stream 0 being the object's own seed. So a single old profile fails exactly as before, a class's profiles fail apart in each instance, and profile streams never collide with instance streams. The checker refuses two profiles of one object with one stream, counting a place as one.
  - **Results unchanged:** the demo and the buffered line, seeds 0, 7 and 123, 20 days, every occurrence (with the new `profile` field taken out) and every object's state and statistics, hashed identical to `master` with a temporary `examples/hash_check.rs`, removed after.
  - **Model files:** `failures` is a list of `{ name, stream?, availability, repair_time }`; the old single object reads as a list of one named "Failures" without a stream and saves as a list, so `models/demo.json` and `models/buffered-line.json` were saved again. ### User code (PR 1a)
[Spec issue 156](https://github.com/MarcHoff94/crabsim/issues/156), ADR 0029. PR 1a, merged as #158 on 2026-11-26, is the engine for objects without geometry; `CLAUDE.md`'s "User code" paragraph says how it works. Decided while building:
- **Calls run right after the event that noted them, never through the queue,** so a model without hooks keeps its events, their order and their sequence numbers. Each call counts toward `ZERO_TIME_EVENT_LIMIT`, so two hooks moving an MU back and forth end in `ZeroTimeLoop`.
- **The trait is `Send + Sync`,** since the catalogue shares a `ModelDescription` between job threads. A WebAssembly host has to fit that.
- **While a distribution is asked, the object stays as it was** (a Station Processing with its work finished, a Buffer not blocked), since the answer comes at that instant: no Blocked and Unblocked at one instant for every MU. `SingleStation::freeze_work` now freezes only work in progress (`Finish::At`), which it always was before.
- **What each call carries:** the MU as a copy, so code reads it in a Drain where it is gone. A Source's entry is its MU being created, its first at Init included; starting MUs get no entry call. Between objects without geometry, Front, Booking point and Rear are one instant, and a hook with several set runs once for each, front first. From a conveyor, all three run at the handover until PR 1b gives Front and Rear their own times.
- **Actions by access:** the hook before Reset only reads; before Init and after Reset, objects haven't started, so only values and timers. Code's changes after Reset carry into the next Init, so a fresh run and a run after Reset differ if that hook changes anything: worth a look in PR 2.
- **Moving an MU** named the object holding it as well as the MU (`move_mu(mu, from, to)`), so the engine found it without searching; since PR 1b the run knows where every MU is, and code names the MU alone. Taken from a Source during its interval, the next MU still comes when the interval ends; taken once ready, the next interval starts at once (frozen if the Source is interrupted). Taken from a Station in work, its exit goes stale (a guard: the exit already sees another MU) and it is not counted as finished. Its old object counts it out, sends retries to those waiting, and gives up its places in lines.
- **`set_work_time`** records a `WorkStarted` again, so a view's completion time follows.
- **A move made by code is a plain `MuMoved`.** The spec's marker comes with the log occurrences in PR 3.
- **Results unchanged:** the demo, the buffered line, the conveyor line and the cross line, seeds 0, 7 and 123, 20 days, with and without pauses and stops by hand: every occurrence and the final state hashed identical to `master`, again after the performance changes below.
- **Performance: 4 to 8% slower on models without hooks, accepted for now by the owner** on 2026-11-26, outside the spec's ±2%, to be looked at again once PR 2's WebAssembly path has given the hot path its final shape. Measured on the first PC against `master` (1d879a0), alternating, medians of 3 rounds of the full benchmark, in events/s: demo headless 17.20M against 18.67M (−7.9%), 10 years 16.81M against 18.11M (−7.2%), buffered line 14.22M against 15.76M (−9.8%), demo kept 10.47M against 11.22M (−6.7%), demo dropped 14.60M against 15.47M (−5.6%), 6,006 objects 7.53M against 7.81M (−3.6%) and dropped 6.39M against 6.62M (−3.5%), conveyor line 11.16M against 11.22M (−0.5%), cross line 13.26M against 13.10M (+1.2%); later quick runs of demo headless gave −4 to −7%. Rounds of `master` alone varied by about ±1.5%.
  - **What was found and fixed,** from 10 to 15% slower at first: `RunError::Hook` held the whole call and a message, 72 bytes in every event's `Result`, now boxed (16); `move_by_code` called `try_to_move_to_successor` back for a default answer, a recursion that stopped it being inlined, which cost the buffered line most; the hook checks at each entry and move now share recording's one check (`EventContext::moved`, `created`); the code path takes the object as `&mut dyn PassesOn`, compiled once; a timer is found by the check that an event's object exists.
  - **What was ruled out,** each measured alone against `master` in a scratch copy, within noise: the two new `EventType` variants, `Distributing::Code`, the larger `EventContext` (72 to 120 bytes), the run's three new fields, `master`'s own run code, `master`'s own object handlers, and aligning every function and branch target to 64 bytes. Taking out the check for calls after each event, or the code path in the move function, or both, recovered 1 to 3% at most. Two copies of the event loop, one per kind of model chosen once per advance, made it about 20% slower, the dispatch no longer inlined, and was undone.
  - **Profiling:** samply 0.13.1 with Microsoft's Windows Performance Toolkit (both now installed on the first PC; samply's own symbol lookup named nothing from these PDBs, so samples were named from a linker map, `-C link-arg=/MAP:...`). The branch spent about 10% more samples evenly across every hot function, the event loop, the move function, the Source and the Station alike, rather than in any one place, the hottest instructions identical (taking the next event off the heap). The tools were thrown away with the scratch folder.

### User code (PR 1b)
[Spec issue 156](https://github.com/MarcHoff94/crabsim/issues/156), ADR 0029. PR 1b gives conveyors and cross conveyors hooks; `CLAUDE.md`'s "User code" paragraph says how it works. Decided while building, for the owner to look at:
- **A move's three moments are the same for both its objects:** the giver's exit at a trigger point and the taker's entry at it run together, front first. Where a conveyor gives, the front is its MU's front crossing its end as the successor reserves a place (the start of Receiving), the booking point the handover, the rear its rear crossing that end. Onto a conveyor from an object without geometry the MU enters with its booking point at the start, so front and booking point are the entry and the rear is its rear crossing the conveyor's start, which the MU's geometry puts behind it. Between two conveyors the rear is the end of straddling. Between objects without geometry all three are one instant, as in PR 1a.
- **The rear into an object without geometry is worked out at the conveyor's speed** from the handover, since the MU is gone from the conveyor whole there (ADR 0023): an interruption of the conveyor or anything else doesn't move it. Onto a conveyor, the rear follows the MU as it really moves.
- **A conveyor's distribution runs as its front MU reaches the end,** and its MUs move on as they were until the answer at that instant, so nothing stands or blocks for an instant, as a Station stays Processing in PR 1a. Hold leaves the MU standing at the end, Blocked when nothing moves. A cross conveyor's runs as it lets the MU in (spec issue 148), a replan stopping at the question and running whole once answered, so that default gives exactly the events of the cross conveyor's own strategy: the first try replanned twice, and events at the same time came in another order. Hold there leaves the MU on its way to the far side, standing there until code moves it.
- **Moving a distribution's moment** (`distribution_on_entry`, an entry trigger point) keeps each answer with its MU until it leaves, so a Buffer holds one per MU; a starting MU, which never entered, is asked when it wants to leave. A call already waiting isn't made twice: a Source asked at its MU's creation would otherwise be asked again as it leaves. A Source's answer at creation waits for its interval: the first try passed the MU on at once and ended in a zero-time loop. At the rear, an object without geometry may have passed the MU on before its rear crosses the conveyor's end, so it isn't asked then; it was asked as the MU wanted to leave. A cross conveyor's moment can't move, since its exit is chosen as it lets the MU in.
- **Moving an MU onto a conveyor from code** puts it on as from an object without geometry, lengthwise with its booking point at the start, if the conveyor takes it now; a cross conveyor takes one only from one of its predecessors, whose side it comes in by. Off a conveyor from anywhere on it, the MUs behind replanning and those waiting offered the room, but not while it is being handed over: to a successor that reserved it, or with its rear still on the conveyor before (ADR 0023). A move by code leaves its object whole at once, so all three of the old object's exit points run then, a conveyor's included (a test). Asked for by the owner on 2026-11-27: `move_mu` onto a conveyor stays as it is, and `place_mu` puts an MU on one with its front, booking point or rear at a given distance from the start, whole at once unless its rear hangs behind the start, where there is room for it with the gap; not on a cross conveyor, which takes an MU only at a side. Placing its booking point at 0 m is the same as `move_mu`, a test.
- **Every run knows where each MU is** (`SimulationRun::location_of`, `HookRun::location`), asked for by the owner on 2026-11-27 for building models in general, so `move_mu(mu, to)` and `place_mu(mu, to, at, point)` name the MU alone. The owner chose a table in every run over one only in runs with code, for now, to see what it costs: `MuLocations` (`src/locations.rs`), written at every move and emptied by a Drain, starting MUs put in at the run's default state (`default_context`, at build, Init and Reset), a window over the MU ids that grows while at least half its slots hold an MU, stray long-stayers in a map. Its cost and how the first version did on a crowded model, measured with the new `crowded-buffer` scenario, are in `docs/design/performance-trade-offs.md`, which the owner asked for on 2026-11-27 to hold every performance trade-off and idea from now on.
- **Results unchanged:** the demo, the buffered line, the conveyor line and the cross line, seeds 0, 7 and 123, 20 days, with and without pauses and stops by hand: every occurrence and the final state hashed identical to `master` (b88185a). Default on every distribution of the conveyor line and the cross line gives the same occurrences and state as without code, a test.
- **Performance: models without hooks within the spec's ±2%,** measured in this cloud container (4 cores, noisier than the first PC: `master` alone varied by about ±3%) against `master` (b88185a), alternating, medians of 3 rounds of one repetition, in events/s: conveyor line 7.03M against 7.09M (−0.8%), cross line 7.72M against 7.86M (−1.8%), demo headless 11.24M against 11.34M (−0.9%), buffered line 9.84M against 9.48M (+3.8%). To be measured again on the first PC.
  - **What was found and fixed,** from 4 to 8% slower on the conveyor scenarios at first, with callgrind (valgrind is in the container, perf isn't): the branch ran only 0.7 to 1% more instructions, but its simulated instruction-cache misses rose by 57%, in `offer`, `replan` and `hand_over`, the functions that had grown. `reserve_with_strategy` had stopped being inlined into `offer`, since the code path called the same copies: its strategies are wrapped in `ByCode` there, as `move_by_builtin`'s are. Everything for code in `hand_over` and `reserve_with_strategy` went into a cold function behind one `has_hooks` check, the conveyor's state for code into one boxed `ForCode` (one pointer, one check as it replans), and a conveyor's rear event is checked in the arm for stale tickets, which its ticket always is but by chance, off the path of the conveyor's own events.

### User code (PR 2)
[Spec issue 156](https://github.com/MarcHoff94/crabsim/issues/156), ADR 0029 as amended on 2026-11-27, `docs/design/code-interface.md`. PR 2, built on 2026-11-27 on `claude/sweet-mendel-u3nr5b`, is WebAssembly: `CLAUDE.md`'s "User code's host" and "User code's bindings" paragraphs say how it works. Decided while building, for the owner to look at:
- **A plain module, not a component (the ADR's amendment).** wasmtime can't read a component instance's memory, so a component couldn't be copied into a checkpoint. The spec's way out, a plain module with a hand-written interface for Rust, was meant for call cost; checkpoints made it necessary. The interface is versioned (1) and written down in `code-interface.md`, and a module of another version is a problem naming both.
- **Functions declare themselves in a custom section** (`crabsim-functions`, a line each with the interface version), which `hook!` writes, so a module needs no call at load to say what it has, and the linker's order of the lines doesn't matter: crabsim keeps them by name.
- **Addresses:** an object is a parameter of type object, an instance's name in the model file resolved to its id when the model is built (a misspelled name is a problem there), and attributes are typed functions in `crabsim-guest`, so neither can be misspelled in the run. `find(name)` is there for code that looks a name up itself. Reading an MU's destination and work plan step isn't offered yet.
- **Random numbers** come from each object's own stream for code, seeded from the run's seed and the object's stream, apart from the object's own numbers, so asking for them changes nothing else. It needed `HookRun::seed` and `stream` in the engine, its only change.
- **A timer calls its own hook function again** with its parameters (`call_after(time, data)`), rather than naming another function, so a module needs no table of its functions. A hook after Init starting an hourly report is the example's `report`.
- **State:** a module keeps it in its memory, which `crabsim-guest`'s `with_state` gives by type, so the same code works natively, where the host keeps it per run. Statics work in WebAssembly too but not natively, where they would last between runs.
- **Native mode** calls the same `Host` the imports call, through a thread-local, so a module behaves the same both ways: a test runs the example's distribution both ways and compares every occurrence and the final state. Its panics are caught; natively a hook is a Rust function, since a panic can't unwind out of an `extern "C"` one.
- **Model files:** `on_entry`, `on_exit` (`at` the trigger points), a distribution `{"code": …, "default": …, "asked_on_entry": …}` and the model's `hooks`, in the reader, the writer, the checks, the schema and `docs/design/model-file.md`. A hook's shape is checked when the file is read, its function and parameters when it is built with its code, each problem where it is written, a class's on the class. `to_description` builds without code, for analysis (`query_model`'s distribution, the window's moves); the CLI, `start_run` and the window build with it (`to_description_in`), so a model with code never runs without it.
- **The models folder's `code/`** may hold a module's sources: the check for source code skips it, at the folder's root only.
- **The CLI** finds `code/` beside the model file, names each module with its SHA-256, and writes log lines with `--code-log`. Storing hashes on runs is PR 3.
- **Not done in PR 2:** log lines as occurrences, references to source, `get_code`, hashes on stored runs, the `performance` table (PR 3); any window for code (PR 4: the window runs models with code, and shows a missing module as a problem, but has no fields for hooks); debugging under WSL with lldb, since this container has lldb but no WSL and wasmtime is built without `debug-builtins`; the analysis treating a code distribution as able to reach any successor (`validate_model`'s warnings and the Paths view read its default today); a module changing on disk while a window has the model open is picked up only when the model file changes or is opened again. Code's changes after Reset carrying into the next Init, as PR 1a noted, is unchanged.
- **Results unchanged:** the engine's per-event code is untouched, and a model without code builds exactly as before, a test comparing every occurrence and the final state of the demo built both ways.
- **Performance:** none on models without code. A call costs about 190 ns, two and a half events (`cargo bench -p crabsim-code --bench calls`, `code-interface.md` and `performance-trade-offs.md`), almost the same natively, so most of it is the engine's path for code, by callgrind: the hook checks at every move once a model has any hook, `move_by_code` and `run_calls`. Not tuned: an idea in the ledger.
- **Tests:** `code-host/tests/wasm.rs` (the example as WebAssembly and natively, checkpoints and Reset with state, timers and log lines, random numbers by seed, fuel, memory, a panic, a refused action, an answer that is no successor, the hook before Reset, modules of another version, importing WASI, without crabsim's functions or with hidden globals, parameters checked), `model/tests/code.rs`, the schema test, the CLI's and `start_run`'s, and the models folder's `code/`. The checkpoint test was checked to fail with the memory copy taken out, after a first version passed anyway because its count happened to be at a multiple of three.

### Agents model to agreed expectations (designed)
ADR 0030, the glossary's "Agreeing and checking", decided with the owner on 2026-11-27 in five rounds. PRs 1 to 4 are merged and PR 5 designed (see the five sections after this one, and ADR 0030's amendments for what changed while building). Spec issue [#162](https://github.com/MarcHoff94/crabsim/issues/162) holds the work, in five PRs; spec issue 156's PR 3 takes the code parts.
- **Front-ends:** MCP, and a generic CLI for agents: `crabsim operations` lists every operation with its schema, `crabsim call <operation> <json>` runs one, `--agent <name>` makes it an agent's, with claims, history and refusals as over MCP (built in PR 2 as `Source::CliAgent`, known by its name). A smaller MCP tool list (#58) is a later round.
- **The process:** the user and an agent first agree what the model must achieve; then the agent builds without randomness and verifies; then adds randomness and validates against data from the real line. If a multi-session project already has agreed expectations, the first step is skipped. The user defines the solution space, as in constraint programming, and the agent must be critical when the data looks inconsistent. The process is described in the MCP instructions and `--help`; agent files or skills may take it over later.
- **A request** holds the user's words exactly, the agent's restatement in precise terms, its expectations by id and its state (open, built, met, broken). The user accepts the restatement and its expectations in one step. Unaccepted expectations block nothing. Requests live in the model file; the changes and runs they refer to are linked by id, in the history and the results store.
- **Expectations:** figures at the end of a run, and limits during it whose first violation is noted with its time and MU. Per measuring period comes later. On a class, `every` or `mean`, said explicitly, planned from the start. Written as one line of text crabsim parses (`every Press.busy_share since start >= 60%`), kept as a string in the model file's top-level `expectations`, a problem naming its position. Their record: id, text, subject, figure, comparison, value with an explicit unit, stage, assumptions, source, so a SysML v2 import maps onto it.
- **Who changes them:** an agent proposes, the user accepts, only the user changes an accepted one (user-only, as `take_model`). An agent may mark one questioned, with its reason. The user is the final instance for now; a reviewer agent with its own role, never the agent editing the model, is a later round.
- **Verdicts:** met, not met, undecided, error. A single run or a live session says met so far. An experiment judges by the 95% interval, "undecided, run more" when it straddles the limit; a limit during the run is not met if any observation breaks it.
- **Stages:** draft, verified, validated, set by crabsim, dropped back when a change breaks a check, and "not checked since change N" until checked. Verification runs when the agent or user asks, and by itself when an agent releases its claim, when the window opens the model and before an experiment; the owner didn't want it after every change, since an agent's rapid edits would start runs for nothing. Validation runs only on request. Each stage has run settings in the model (length, warm-up, observations), which an expectation may override.
- **Deterministic runs:** a run option, not a second model: failures off and every time drawn from a distribution at its mean, also for random attributes added later; code's `random()` left alone, since it is seeded, with a warning when a verification check rests on a hook that calls it. The owner's practice: build a model without randomness first and add it once that is sound.
- **Reference figures:** measured values with tolerances and their source, validation-stage expectations. Event logs from the line (MES, SCADA, CSV) compared with a run's are designed for; fitting process times or failures from them is later.
- **Bounds checks** without a run warn of an expectation that can't be met or contradicts another, such as a throughput above what a Station's process time allows.
- **One vocabulary of figures** for rules, expectations and code: everything crabsim measures (shares of time, MUs in and out, throughput, contents now, mean, median, most and fewest, lead time, a conveyor's length taken and crossing time, a cross conveyor's switching share), an object's state now, and an MU's class, next destination and plan step. Each now, since start or `last <time>` where it makes sense, the stretch kept in fixed buckets (such as 60 of a minute for an hour) only for figures something names. An operation lists every figure with its meaning and unit. Figures the model defines itself, such as a difference of two, come after user-defined attributes.
- **Rules:** when/then lines in order, with and/or. When: the MU's class or next destination, a figure compared with a value or another figure, the time of day. Then: a named successor; the successor with the smallest or largest figure among all or a listed few, saying `among those free` (the default) or `and wait`; round robin or weighted among a listed few; default. On entry, a rule may set the MU's process time from its class or a table. Hold and release stay code. The built-in strategies stay as they are; expressing them as rules is a later idea.
- **Code (spec issue 156's PR 3):** sources in `code/<module>/` are the truth, changed only through operations with claims, history, undo and "changed outside crabsim"; crabsim builds the `.wasm`. crabsim installs a pinned Rust once per user in its own data folder, one per interface version, starting the install being user-only, allowable once per folder or for good; a later installer ships it. crabsim writes the crate's `Cargo.toml`: `crabsim-guest` alone, no build scripts, offline. The owner: a user who allows other crates does so at their own risk, so that is a user-only setting per folder. A hook is tested at a real situation, such as the 100th MU at X, answering with the figures it read; saving such tests as checks comes later.
- **The decision record:** an opt-in recording of each decision by a rule or code, with the MU, the figures read with their values and the answer, read by an operation and shown in the window for a selected MU.
- **Status:** one operation and one panel: the stage, every request with its state, each expectation's verdict, the questioned ones with their reasons, what's not checked since the last change, and the next step. Both the window and chat matter to the owner.
- **Names:** Request, Expectation, Reference figure, Rule, Stage, Verdict; Verification and Validation.
- **Order of work:** (1) the vocabulary with time scopes, expectations, verdicts and deterministic runs; (2) stages, requests and agreeing, with the status operation and the agent CLI; (3) rules; (4) reference figures and bounds checks; (5) the decision record.
- **Later rounds:** a reviewer agent's role; a smaller MCP tool list; agent files or skills instead of MCP instructions; reading SysML v2 text (researched on 2026-11-27: final since 2025, MIT Rust parsers `sysml-v2-parser` and `syster-base`, structure and requirements map well, behaviour and randomness don't, manufacturing hasn't adopted v2 yet); event logs and fitting; model-defined figures; an installer with the toolchain; saved tests of hooks; the built-in strategies as rules.

### Process times by MU and which MUs an object takes (PR 5, merged)
Designed with the owner on 2026-11-28 in seven rounds after PR 4 (ADR 0030's and ADR 0026's amendments of that day, the glossary's Current step, merged with #168), and built on 2026-11-28 in a cloud session on `claude/sleepy-pasteur-fud8ss`, with ADR 0030's fifth amendment, merged as #170. It is spec issue 162's PR 5, ahead of the decision record, PR 6. The design:
- **A Station's `process_time`** is a time, or `{"rules": [...], "default": ...}`: when/then lines, each action a time or `default`, with the distribution rules' conditions (class, time of day, another object's state, figures) but not the destination, and with `step = <class or instance>`, which distribution rules gained too. The default is the Station's own time (interventions, Keep changes, weighted ranking, the Paths view, no line holding), inherited as a whole. A plan step's own time wins on plan. Stations only, decided at entry. Bounds use the lines' smallest and largest time. A Rules box in the window; the command language later.
- **`step`** is an MU's current step, by the class or instance it names: its detour's while it has one, else its plan's current step's, none without a plan or past its last step. A listed class covers itself, derived classes and their instances, an instance itself alone.
- **Which MUs an object takes:** `X.step always in …` and `X.class always in …`, with `not in`, a limit on any object MUs enter, `every` allowed; listed names must be classes or instances (a problem otherwise); an MU without a step breaks a `step` line. A check, not a constraint, watched only at the objects an expectation names, in runs that judge expectations, not the window's live session. A value is the number of MUs that broke it; not met names the first with its time, object, MU, class and step. No bounds.

What was decided while building:
- **The open point is solved without restricting conditions:** whoever hands an MU to a Station with time rules decides its time as it enters it (`model_object::enter_deciding_time`, `ModelObject::enter_timed`, a Station's `take_in`, from `try_to_move_to_successor_with_strategy`, a conveyor's `hand_over` and `HookRun::move_mu`), reading the others and itself (`rules::Peer`, `Peers`, `Reads`, `SuccessorContainer::statistics_and_kind`), the giver having counted the MU out. So lines may read another object's state and figures, the giver's included, and no zero-time event was needed.

A first version boxed them on the Station, which grew `ModelObject` from 592 to 600 bytes; the size test caught it. They and the watches sit behind one pointer in the context (`Extras`) and in the run (`RunExtras`): with a pointer each, the context grew from 248 to 264 bytes and the run from 576 to 672, and the 6,006-object model recording occurrences (`large-dropped`) ran about 5% slower; at 256 and 592 it came back within noise. `EventContext::decides_times` is whether the context has either, so a run that only watches enters MUs through `enter_deciding_time` too, to the same effect.
- **Inlining kept:** the second way into a Station first stopped the compiler inlining a Station's entry (`take_in`) and `ModelObject::process_mu_entrance` into every move, about 1% more instructions on the demo, which cachegrind's per-function diff (`cg_diff`) showed; `#[inline(always)]` on both put instructions back where `master` has them. Recorded moves check user code and watches with one flag (`beyond_recording`), as they checked user code alone before.
- **`default` is required** in the rules form, a line's time has its unit (a bare number is a problem), starting MUs take the Station's own time.
- **Watches** (`src/watch.rs`): `SimulationRun::watch`, checked in `EventContext::moved` and `moved_by_code` behind `watching`, `RunState::watches`; the model crate's `Model::entry_watches` builds them for bound expectations (building the model once more, only when one is a limit on which MUs an object takes) with the names for the first break, `observe` takes them and `first_violations` never replays them. `Violation` gained `class` and `step` (`none` without a step) and lost `Copy`; the store's `violations` gained `class` and `step`, tables version 10, upgraded in place; `run_results`' violation leaves `value` out for these and says `35 MUs broke it` as what was reached.
- **A bug from PR 3 fixed:** an MU class alike another in every value (such as `Tote`, the built-in MU's size) shared the first one's MU kind, named after it, so `class = Tote` never held. Now a Source's MU class gets a kind of its own when deduplication would hand it another class's (`ModelDescription::add_separate_mu_kind`, `plan`); models whose MU classes all differ keep their ids. `models/conveyor-line.json` is one that changed: its MUs' kind id, nothing else.
- **`step` and `next_destination`** read the same destination; `step` matches by what a listed name stands for. Destinations standing for the same objects are one in a run (`add_destination` deduplicates by members), so a listed instance also matches a step naming a class whose only instance it is.
- **Keep changes** in the window keeps a Station's lines, saving its own time as their `default` (`Workspace::keep_changes`).
- **Not done:** the command language for process-time lines (`set X.process_time` takes JSON only through `edit_model`); the Paths view showing which successors a rule prefers (left from PR 3); the decision record (PR 6). The window's Rules box for a process time was tested through `ui/tests` only, not tried in a window, as PR 3's was.
- **Performance:** every occurrence and the final state of the demo, the buffered, conveyor and cross lines and the model files hash the same as `master`, `conveyor-line.json` once MU kind ids are masked (its Tote now has a kind of its own). The benchmark is in `docs/design/performance-trade-offs.md`.
- **Tests:** `tests/time_rules.rs` (each condition, the step, a plan step's own time winning, `default` and an intervention, a batch Station deciding at entry, the giver and a conveyor read, a stretch only buckets can tell, Reset and a copy, no rules same as before), `tests/watches.rs` (class and step, in and not in, an MU without a step, a detour's step, the first break, warm-up, Reset and a copy, watching changes no result, `step` in a distribution rule), `model/tests/time_rules.rs` (read, saved canonical, inherited as a whole, a plan step winning, problems where each line is written, `step_covers`, limits read and checked, renames, watched and judged, bounds from the lines), `catalogue/tests/time_rules.rs` (through `call`: refused, renamed, run, judged with the first MU in `run_results` and the store, a ninth-version store upgraded), a CLI test, and `ui/tests/attributes.rs` (the Rules box's form, the workspace saving it, Keep changes keeping the lines). ### Reference figures and bounds (PR 4, merged)
Spec issue 162's PR 4, built on 2026-11-28 on `claude/funny-keller-ajlmxv` and merged as #168, with ADR 0030's fourth amendment. What was decided while building:
- **A reference figure is `=` with a tolerance,** `Drain.throughput_per_hour since start = 4100/d ± 3%` (`±`, `+-` or `+/-`, saved as `±`), at the validation stage with its `source`: the tolerance in the figure's own unit, or a percentage of the value for a figure not in shares, so `70% ± 5%` is 65% to 75% and `4100/d ± 3%` relative, as people read them. Not on a limit, a state or another comparison. Judged by the 95% interval: met inside the band, not met wholly outside, undecided otherwise with the observations that would decide it; one observation or a deterministic run by its value. Nothing else marks a reference figure, so requests, stages and agreeing are unchanged. `validate_model` warns of a validation `=` without a tolerance and of a reference figure without a `source`. `run_results` gives `tolerance` and `band`.
- **Event logs are designed for, not built** (ADR 0030's amendment): a log's MUs entering and leaving objects are what a run records as occurrences, so a reference figure will later take its value from a log, its `source` naming it.
- **Bounds** (`model/src/bounds.rs`, `Model::expectation_bounds`, among `Model::warnings`): an expectation crabsim works out from the model alone can't be met, or contradicts another. A figure's range; capacity; failures at verification or of an object without a profile, pauses, receiving without a conveyor in; a maximum flow in whole MUs (Dinic's, without recursion) through what lies upstream, each object passing at most its own pace in the stretch (a Source an MU an interval, a Station its capacity per shortest process time, its own or a plan step's, a conveyor an MU per the MUs' least booking-point spacing at its speed, a cross conveyor an MU per its shorter side), from Sources and what each object can hold as the stretch begins (at Init its starting MUs, later its capacity, an unlimited Buffer its starting MUs and what can reach it by then), for MUs in and out, throughput and a Station's busy share; a shortest way (Dijkstra's) of work, dwelling and crossing for lead and crossing times; an object in a loop (Tarjan's) by its own pace alone; contradictions of the same figure of the same instance in the same stage and settings (`mus always` being `max_mus since start`), and shares of one object's time that can't add up to 100%. A model with code gets only range, capacity and contradictions. Each is certain but one: **a since-start throughput** counts from the Drain's first MU, so MUs arriving together just before the end could make it anything, and it is bounded as if that MU came as early as it can. Found while building: bounding it as if it came as the stretch began gave a false warning for a 10-place Station of an hour over 2 hours, which reaches 19/h.
- **Where bounds show:** `validate_model`'s warnings at the line, `get_status`'s `cannot_be_met` (kept for the last 8 models by hash, since the window reads the status every few seconds), its `next`, ahead of checking (change the model or a proposed one before the user accepts it; change the model or question an accepted one; for the user, change the model, or change or remove it: found when `catalogue/tests/stages.rs`'s Press at 5 s made its accepted 70% unreachable, where the next step had been to check), the CLI's `status` notes and the window's Status tab in red.
- **Not done:** setting an MU's process time on entry and the Paths view showing which successors a rule prefers (left from PR 3); the warning for verification resting on code's `random()`; `get_attributes` showing expectation fields; lower bounds on throughput or shares (blocking makes them unknowable without a run); a conveyor's MUs held or a cross conveyor's switch and release times in its pace.
- **Performance:** nothing on the per-event path; bounds are worked out on request. On 429 copies of the demo with five expectations, three `every` over 429 to 3,003 instances, 69 ms; a line of 3,000 Stations with `every Station.working_share` about 1.1 s, quadratic, with a one-pass idea in `docs/design/performance-trade-offs.md`.
- **Tests:** `model/src/expect.rs` (tolerances in and out, errors at their character, a band judged met, not met and undecided), `model/src/bounds.rs` (the flow, loops, compatible lines), `model/tests/bounds.rs` (each kind of bound past its edge and not at it, a stretch after a warm-up with held MUs, the batch Station's throughput, a loop, code, reference warnings, and **no bound below what a run of `demo`, `buffered-line`, `conveyor-line` and `cross-line` reached**: each object's figures from deterministic and random runs, since start and over the last hour, after a warm-up or not, written as expectations that ask exactly that, none of which may be warned), `catalogue/tests/bounds.rs` (an agent learns before anything runs, the next step through proposing, accepting and questioning; a reference figure validated, with `tolerance` and `band`), a CLI test of `status`, and `ui/tests/status.rs`. ### Rules (PR 3, merged)
Spec issue 162's PR 3, built on 2026-11-28 on `claude/admiring-wright-qyh2ow` and merged as #167, with ADR 0030's third amendment. What was decided while building:
- **Rules are a distribution strategy** with a `default`, as code's is, and in the engine one more `Distributing` kind on code's cold path (`src/rules.rs`, `move_by_rules`, `reserve_by_rules`, `choose_exit_by_rules`), so models without rules give exactly what they did (every occurrence and the final state of the demo, the buffered, conveyor and cross lines over 2 days hashed against `master`).
- **The line form:** `when <conditions> then <action>` or `otherwise <action>`; `and` binds before `or`, no brackets; names may not hold ` and `, ` or `, ` then ` or `, `. Conditions: `class = ...` (a class standing for its derived MU classes), `destination = ...`, `time of day <cmp> hh:mm`, `<instance>.state now = ...`, `<instance>.<figure> <scope> <cmp> <value or figure>`. Actions: `to`, `smallest`/`largest ... [of ...] [among those free|and wait]`, `round robin [among ...]`, `weighted among ...` (the object's own ranking: its default must be weighted), `default`. A rule never reads the object deciding.
- **What a rule reads:** figures the statistics keep as the run goes (`crabsim::rules::readable`), so no median or fewest; a stop by hand reads as failed. A cross conveyor's rules choose among all its exits, overriding its exits' lists, as code does; `default` falls back to them.
- **Stretches** are 60 buckets kept by the rules that read them, of the object read, rolled by the run before an event that reaches a boundary (see "Performance" below and the ADR); a stretch reads up to one bucket long, and since start while the run is younger.
- **Not built:** on entry, an MU's process time from its class or a table; a rule's line in the window beyond a text area; the Paths view draws R for rules but not which successors a rule prefers; rules in the command language (`set X.distribution` takes JSON only through `edit_model`).
- **Performance:** a first version kept the buckets in the statistics keeper: 2.2 to 2.5% more instructions with a check on each change of state, and still about 4% of the demo's wall time once the check moved to the run loop, from the keeper's changed layout. With the buckets in the rules and the keeper as before, models without rules are within ±2% on every scenario measured. See `docs/design/performance-trade-offs.md`.
- **Tests:** `tests/rules.rs` (each condition and action, among those free against and wait, a stretch against since start, a conveyor and a cross conveyor, Reset and a copy), `model/src/rules.rs` and `model/tests/rules.rs` (lines in and out, problems where each line is written, a run), `catalogue/tests/rules.rs` (refused, renamed, explained by `query_model`, run), and the window's distribution field. Mutations caught: no rolling, no renaming in rules, a class not standing for its derived classes. The window's Rules box and the Strategies view's R were tested only through `ui/tests`, not tried in a window.

### Stops (as agreed before spec issue 122)
- **Interruption** is the cause (a failure or a pause). **Stop** is the resulting state of the object. A failure from t=20 to 30 plus a pause from t=25 to 35 is two interruptions and one stop from t=20 to 35.
- **Failure** is unplanned, with random timing. **Pause** is planned and commanded from outside, and doesn't count against availability. They are independent of each other. *Built on Stations only, including overlap. A second failure while already failed is still discarded.*
- **Forced failure** is a failure the user starts and ends by hand, to see what happens if a machine breaks down now. It counts as a failure, and random failures carry on underneath it. It has its own stop cause, `ForcedFailure`, between `Failure` and `Pause` in seriousness. *Built on Stations only.*
- **Reporting overlapping interruptions:** each begins and ends as its own occurrence, and a full state reports the most serious as `stop` and lists all of them in `interruptions`. *Built.*
- **Completion time** = entry + process time + time spent stopped. Overlapping stops count once. *Built on Stations, including overlap.*
- **A stop by type** (*built only for Stations*):
  - **Station:** takes no MU, releases no MU, work is frozen. A whole Station stops at once, whatever its capacity.
  - **Source:** creates no MUs, and its next creation moves later by the stop's duration.
  - **Buffer:** as above.
  - **Drain:** refuses MUs, so predecessors become `Blocked` and retry when it's back.
- **Failure time bases**, configurable, with not every object needing all three (*not built, behaves as simulation time*):
  - **Simulation time (default):** all time counts, whatever the object is doing, including during a pause.
  - **Working time:** idle and blocked count, and only a pause freezes the clock.
  - **Processing time:** only time actively working on at least one MU counts, once however many MUs are in work. A finished MU waiting to leave doesn't count.
- **Availability** is measured against the chosen time basis, so a rarely busy Station on a processing-time basis is available more of real time than its setting. That's expected.

### Moving MUs
- **Push** is the current concept. **Pull** is planned, as a setting on the *receiving* object, where the successor chooses which MU it wants from its predecessor. Only build a seam for "which MU leaves" now, not pull itself. Mixed push and pull cases get decided when pull is designed.
- **Exit strategy** picks which MU leaves, and **distribution strategy** picks which successor gets it. They're two separate rules. The default exit strategy is one at a time, earliest finished first, ties broken by entry order. More strategies may come later. *Not built as a seam.*
- **Under push, MUs can't overtake within a Station**, because successors belong to the Station rather than to one MU. Only pull could change that.
- **Blocked predecessors:** the longest-waiting one retries first, and each is listed once. Built, including at one instant: retries run before other events at the same time, and offer only the successor that sent them.
- **Reproducibility:** the same seed on the same version always gives identical results. Results may differ between versions when behaviour changes on purpose.
- **A move takes no simulation time,** and the UI shows it that way: the MU jumps straight to its new object. Transport time belongs to a conveyor (spec issue 133), on which MUs glide, and a handover from a conveyor takes until the MU's booking point has crossed its end.

### Running a simulation (built, except where noted)
- **Controls:** Init, Start, Halt, Reset. Halt avoids clashing with Stop and Pause, which happen to objects.
- **Init is its own step**, the first step of every run: t=0, every object's init in id order, first events queued but not processed, even those due at t=0. Start does Init if needed, then advances. Start and Halt are commands on a live session.
- **Reset** returns objects to their default state and keeps them in the model. Every run MU is deleted, and configured starting MUs come back as fresh copies. The same seed replays the same run.
- **The default state is what the user configured**, and can be changed. Today configuration changes are only allowed after Reset, except a Station's process time. That can change during a run, as an intervention: the MU in work keeps its time and the next MU uses the new one. *Built.* The agreed rule for later is that every attribute can change during a run, so each one needs its mid-run behaviour defined (see "AI-native").
- **Control order:** Init only from the default state, advancing requires Init, Reset allowed at any time. Violations return errors rather than panicking.
- **A run advances only when asked** and has no end time of its own. `advance_to(t)` includes events at t. Speed control belongs to the caller.
- **A run executes on one thread at a time.** A live session still creates its run on its own dedicated thread, though a run can now move.
- **Occurrences** are returned by each advance today. Views get no callbacks. A run can also be asked for its full typed state. "We might add more states later." A run records only when asked.
- **MU ids** are unique across the model.

### Statistics (built for what today's model has)
See `docs/design/statistics.md`, ADR 0003 and ADR 0004. Objects keep fixed-size, always-on statistics at two levels: machine state and MU time. Warm-up is a `clear_statistics()` call, and per-MU data exists only through recording occurrences. Pause and overlap are built on Stations only. Capacity above 1, dwelling time and the other time bases aren't built, so their numbers stay at zero or at today's behaviour until step 7.

### User code (not built)
The owner wants users to add their own source code later. The decisions so far:
- Each object has fixed init and reset parts that **users can't change**. For example, Reset always deletes all MUs.
- A second user phase runs after the fixed phase **has finished for all objects**, in id order, for both Init and Reset.
- User code must be deterministic and fit in a checkpoint, and objects that use none pay nothing for the feature.
- How the code gets in is decided: WebAssembly hooks acting through crabsim (ADR 0029, [spec issue 156](https://github.com/MarcHoff94/crabsim/issues/156)). The user phase is the hooks after crabsim's own Init and Reset, with hooks before them too.

## First-time experience (built)

[Spec issue 78](https://github.com/MarcHoff94/crabsim/issues/78), decided on 2026-11-09 and built in PRs 80 to 85. The review and the decisions are in `docs/design/first-time-review.md`.

- **Goal:** a newcomer who hasn't read the docs opens a model, runs it as long as they choose, and can say its throughput and which Station is the bottleneck, within 5 minutes. Changing one thing and comparing is the next goal, deferred until after building.
- **Starting:** with no `--models`, the window opens `crabsim-models` in the user's Documents, made on the first start with the demo saved through the catalogue. `list_models` lists only `.json` files with `format_version`.
- **Explaining:** hover text on every control, worded from the glossary. One fixed colour per state for the whole app (`view::rgb`), for utilisation charts later too. No canvas legend: hovering an object names its state, and a ? opens what each state means for its type, with the model's own `state_notes` beside crabsim's meaning, never instead of it. The Editing tab is the Agents tab.
- **Inspector:** statistics per type, Busy rather than Working, a Station's process time once, and a Keep changes checkbox beside Reset that saves changed values to the model file through `edit_model`, or else Reset names what it drops.
- **Speed:** Animate off makes a live session race (`set_animation`), recording nothing and computing as fast as a headless run on the demo, about 10% slower on 6,006 objects, where an animated session at 1,000,000 times took 65% longer. `go_to` goes back or on. Halted, a session records again.
- **Results:** a Results tab with each Drain's throughput and lead time, every Station's shares, sortable, and the likely bottleneck by the rule in `catalogue/src/bottleneck.rs`, which `find_bottleneck` applies to stored runs.
- **Deferred:** comparing before and after a change in the window, through experiments and `compare_runs`. The second walkthrough, on 2026-11-10, met the goal in time but found early results presented as final (findings 13 to 16 of the review).

## UI design

Decided with the owner on 2026-11-07, in a grilling session. Steps 1 to 5 of its order of work are built, and the UI itself isn't yet. The technology research is in `docs/design/ui-technology-research.md`, and the prototype's results in `docs/design/ui-prototype.md`. Like the rest of "Agreed design", don't reopen it without a reason.

### Who, where and what matters
- **Who:** the owner first. Later it's shared as a program to download, with no hosted service or accounts. Nothing should rule that out, but no effort goes into it now.
- **Where:** engine and window are always on the same PC. A long run on a bigger machine is a headless run with no UI.
- **Priority, by default:** building models first, then smooth, good-looking animation, then debugging. Animation matters because it's how non-technical people understand a model and come to trust it. Like performance, this is a default and not a rule: it can be overturned case by case, given real reasoning and a trade-off worth making.
- **Views:** a 2D view now. A 3D view **will** come later, as a second view of the same model, not a replacement. 2D stays for building and debugging, and 3D is for showing and watching. Keep that move in mind in every UI decision.
- **Scale:** up to 6,000 objects. The whole model can always be drawn, with pan and zoom, and every object always shows its state as a colour. MUs appear only when zoomed in far enough and running slowly enough to follow, drawn in the object that holds them. Above that, objects show counts and state only.

### Technology
- **Bevy with `bevy_egui`,** settled by the prototype and recorded in ADR 0006, with eframe and a custom wgpu canvas as the fallback. Bevy won because 2D and 3D share one renderer and one world, so the 3D view costs least, and its forms and panels are egui, the same as eframe's. Its price is upgrade churn, heavier builds and an ECS to learn.
- **Rules that limit the risk:**
  - The engine never depends on Bevy, and Bevy's ECS stays in the UI crate, so ADR 0005's storage is untouched.
  - The Picture lives in the engine library with no Bevy types, and Bevy only reads it.
  - Panels are plain functions taking `&mut egui::Ui`, so they could move to eframe. A wrong choice then costs the canvas, not the whole UI.
  - Bevy's version is pinned, and upgraded only when there's a reason.
- **ADR 0006** records the choice and what it costs, such as builds of 4 to 8 minutes clean and a UI that must show nothing changing while halted.
- **Toolchain (done):** Rust 1.91.1 was too old (Bevy 0.20 needs 1.97.1, egui 0.37 needs 1.95). It is now 1.99.1, pinned in `rust-toolchain.toml`, with a new baseline. The update changed no result.

### The prototype (done)
Throwaway, on `prototype/ui-bevy`, never to be merged, with its results in `docs/design/ui-prototype.md`. Every mark passed: 6,006 objects at 367 to 484 frames per second, a real session at 3,600 times real time with no frame over 33 ms, and a halted window at 0.006 CPU seconds per second. The owner tried it by hand. It answered these four things:
1. **Scale:** 6,000 flat objects with state colours, 5,000 gliding markers and labels on zoom, at a steady 60 frames per second on the owner's AMD Radeon RX 9070 XT. Compare sprites with flat meshes under an orthographic camera, since that decides how cheap the 3D view really is.
2. **Real session:** a live session at 6,000 objects and 1 simulated hour per second behind a window, on a real clock, with no visible stutter. That's about 1.9M occurrences per second by calculation. Nothing has driven a session on a real clock for long, so this is needed whatever the technology.
3. **Panels and canvas together:** dragging from an egui palette into the canvas, clicks reaching the right layer, selecting one of 6,000 objects, and little CPU while Halted.
4. **Build times,** clean and incremental, judged rather than held to a limit.

If 1 or 3 fails, try eframe. If 2 fails, the problem is in the session, not the technology.

### Structure
- **Workspace (built):** the engine stays at the repo root with its tests and benchmark. The member crates are `model/` (`crabsim-model`), `cli/` (`crabsim-cli`) and the UI, `ui/` (`crabsim-ui`), the only one that isn't a default member, so `cargo test` and `cargo bench` at the root never build Bevy (ADR 0009). Run the UI with `cargo run -p crabsim-ui --profile ui`, a release profile without LTO that rebuilds in seconds.
- **Picture (built):** `crabsim::Picture` in `src/picture.rs`, logical state only, what is where and since when. Feed it every session output in order. Visual state, such as where a marker is drawn on screen, stays in the UI.
- **CLI (built):** a simple headless CLI. It runs the demo model with `--seed` and `--length`, the length written as the UI shows time, then prints each object's final statistics, each Drain's throughput and mean lead time, and how many events it ran in how long. A run error still prints the statistics up to it. Since slice 1 of the model file it also runs a model file, with `--model`, and it lives in `cli/`. `--inplace`, `RunView`, the terminal table and the topology text are gone.

### Model data for the UI
- **Names and positions (built)** on `ModelDescription`, as optional fields: `set_name`, `set_position`, `set_dimensions`, with getters, `kind` and `object_count`. Stage 1 writes them by hand for the demo, with no automatic layout. Drag and drop will later write the same fields. The run ignores them, so a headless run pays nothing.
- **Units:** metres for everything. Position is the object's centre, as x, y and z, with z = 0 for now.
- **Dimensions (built):** length, width and height, plus a rotation around the vertical axis in degrees. All optional, with a default size per object type: placeholders of 2 × 1.5 × 1.5 m for a Station, 2 × 1 × 1 m for a Buffer, and 1 m each way for a Source or Drain. Stage 1 draws objects to size, and height waits for 3D. They are **visual only**: MU moves stay instant whatever the distance. Dimensions matter for results only in future transport objects such as a conveyor.
- **Layout image** (with drag and drop, step 3 of the order below): an image of the real site under the model. Its scale comes from clicking two points and entering the real distance. One per model, lying flat, and the floor in 3D. A headless run and the CLI never load it.

### UI stage 1
- **In:** the demo model drawn in 2D with state colours and contents, MUs shown in the object that holds them, Init, Start, Halt, Reset, speed and time mode, shown time, step forward and back, jumping to an earlier time, Pause, forced failure and process time changes on a Station, an inspector, and pan and zoom.
- **Out:** building or editing a model, save and load, scale work beyond a stress check, and polish.
- **Window:** a fixed layout with no docking yet. The top bar has Init, Start, Halt, Reset, step back and forward, jump to a time, speed, time mode and shown time. The 2D view is in the centre, and the inspector is on the right. Defaults are continuous time mode at 60 times real time, which is about 30 events per second on the demo by calculation. Speed is on a logarithmic slider. When playback can't keep up, the top bar shows the speed actually achieved. A run error shows as a banner, and going back out of it stays possible.
- **Inspector:**
  - **State:** type, name, process state, contents and remaining time.
  - **Why it's blocked:** the MU it holds and each successor's state, such as "holding MU 17: Station 4 is working, Station 5 has a forced failure".
  - **Why it's stopped:** every active interruption and since when.
  - **Process time:** current and configured.
  - **Statistics and waiting predecessors:** these come only from a full state, so the UI calls `request_state` about twice a second while something is selected, and never otherwise.
- **Moves are instant:** an MU is drawn in the object that holds it and jumps straight to the next one, with no glide. The owner decided this after trying the prototype: gliding suggested travel time that doesn't exist. The gliding code is kept for a future conveyor, which has real transport time.
- **Interventions on the time display:** each shows as a mark. Going back past one asks for confirmation, saying how many will be lost. The engine rule stays that going back drops later interventions.

### Engine additions for stage 1 (built)
All built in PR 21, as planned except where noted. The benchmark gave identical results and speed within noise.
- **Forced failure,** on Stations for now: an intervention the user starts and ends, with no sampled repair time. It counts as a failure in statistics and against availability, random failures carry on underneath it, and an overlap is one stop. Built as its own stop cause, `ForcedFailure`, with `force_failure` and `end_forced_failure` on the session. It **can't reuse** `StartFailure` and `EndFailure`, because each random failure schedules the next only when it ends. Reusing them would start a second chain of failures, or, when a random failure came due during a forced one, discard it and end that Station's random failures for the rest of the run. *Cost:* two event kinds, handled only at a stop.
- **Changing a Station's process time** during a run: an intervention at shown time. The MU in work keeps its time and the next uses the new one. It goes in the intervention log, so replay and going back work. It applies directly to the run, as clearing statistics does, rather than as an event, because a time inside `EventType` would push `ScheduledEvent` past its 32 bytes. *Cost:* nothing per event.
- **Reset keeps changes,** a session setting, off by default, read when Reset is pressed. When on, a changed process time becomes the new default state, and Pauses, forced failures and clears of statistics are dropped. A change already dropped by going back is not kept: the values come from the intervention log, which holds what is true at shown time, rather than from the run, which may be ahead or mid-replay. Replaying the whole intervention log in the next run, as saved intervention scripts, could come later as its own feature.
- **`step_back`:** a session command that finds the previous instant by replaying from the nearest checkpoint, at about the cost of a `go_back`, or two when it has to fall back to an earlier checkpoint. The UI keeps no list of instants, so memory stays flat. An instant is a time with occurrences, so an event that records nothing, such as a stale exit, makes none.
- **Configuration in `ObjectState`:** a Station's current and configured process time, for the inspector.
- **Added on the way:**
  - **Every active interruption in `ObjectState`:** a picture taken while a failure and a pause overlapped used to lose the pause, because state reported only the most serious. Since UI slice 3, each comes as an `Interruption` with when it began, for the inspector's "since when". A Station keeps one start time per cause, written only when an interruption begins, so nothing per event.
  - **`NotAStation`:** `SessionError::CannotPause` became `SessionError::NotAStation`, and the run gained `RunError::NotAStation`.

### What the engine gives a UI today

All of it is on `LiveSession` in `src/live_session.rs`, and `CLAUDE.md` has the overview.

- **Commands:** `start`, `halt`, `reset`, `set_speed`, `set_time_mode`, `go_back`, `step_forward`, `step_back`, `locate_step_back`, `set_reset_keeps_changes`, `set_end_time`, `request_state`, `pause`, `resume`, `force_failure`, `end_forced_failure`, `set_process_time`, `clear_statistics`.
- **Session outputs** (`SessionOutput`), read from a channel: `Occurrences`, `ShownTime`, `State`, `Status`, `Error`, and `StepBackTarget` in answer to `locate_step_back`.
- **Rebuilding the picture:** `crabsim::Picture` takes every observation in order and keeps what the user knows at shown time. One full state at Init, then occurrences give each object's contents, process state, every active interruption and remaining time. `WorkStarted` and `MuCreated` carry durations, so a progress bar needs no further messages. Tests prove this on 3 models: a line with failures, with overlapping pauses or forced failures, a line that blocks, and the full demo. A further test takes a picture while interruptions overlap. Buffer is left out, because its movement is broken.
- **Model data:** a `ModelDescription` holds names, positions and dimensions in metres. A session builds its run from a closure, so a UI keeps the description beside the session to draw from.
- **Statistics:** `request_state` gives exact numbers for the instant on screen in a few milliseconds.
- **Going back:** usually under 15 ms, and up to about 400 ms for far jumps on a large model past the memory budget. See `docs/design/first-profile.md`.
- **Reading has to keep up:** past 256 unread observations a session stops releasing, so a UI drains the channel every frame. At high speed, one session output can hold up to 1,000 instants, so it can't draw each of them.
- **The boundary:** a session sends about 2.5 occurrences per event. The research found that even a UI in another language wouldn't need them: the Picture could stay in Rust and send one small message per frame. This matters only if the technology changes.
- **Changing a model:** a session builds its run once, from a closure, so a changed model means a new session. Apart from a process time, which can change during a run and be kept by Reset, configuration changes have no API yet.
- **Determinism:** nothing in a UI may affect results. Same seed and same interventions, same outcome.
- **Domain language:** use `GLOSSARY.md` in the UI too, such as Halt for the whole run and Pause for an object.

### UI stage 2 (built)

Designed and built on 2026-11-08, [spec issue 63](https://github.com/MarcHoff94/crabsim/issues/63), whose status section and comments hold every decision and what changed while building. In short:

- **A models folder, always:** `crabsim-ui --models <folder>` reaches the folder only through the catalogue, as `Source::Ui`, which counts as the user, and holds `.crabsim/user.lock`. A second window on the folder is refused with a banner, and while a window holds it the CLI's changing commands are refused. The Models panel lists the model files, marking those with problems, and a model clicked runs, or shows its problems instead. Unplaced instances are laid out by the window, and saved only when the user moves an object (see "Moving objects" below).
- **Seed and end time** in the top bar. The seed changes only before Init or after Reset and stays for the window. The end time is a live-session setting (`set_end_time`, status `ReachedEnd`) at which a run halts exactly.
- **Picking up changes:** `Workspace::check` notices the open file changed (size and modified time, then its hash), and the window uses the new model at once with no run in progress, otherwise on Reset. A watcher thread wakes an idle window when the open file or the edit state changes. A file changed outside crabsim is marked, with Adopt.
- **The inspector's attributes:** before Init or after Reset, every attribute of the selected instance with where its value comes from, changed in the model file through `edit_model`, each restored on its own, and "Change anyway" as a one-change take-over. During a run, the interventions as before.
- **The Editing tab:** the edit queue with the user's controls, each checked against the latest queue before acting (`Workspace::act`). Taking the right asks first, and the agent waits first in line.
- **The code:** `ui/src/workspace.rs` (folder, models, layout, changes, attributes, queue), `ui/src/attributes.rs` (the inspector's fields), `ui/src/editing.rs` (the queue), `ui/src/view.rs`, and `ui/src/main.rs`, which only draws. Tests in `ui/tests/` use a real catalogue on a temporary folder, agents played by catalogues opened as `Source::Mcp`, and a real session on a fake clock.
- **Moving objects (after stage 2, 2026-11-09):** the owner expected to drag objects, as the throwaway prototype did, and stage 1 had made every drag pan. Before Init or after Reset a left drag on an object now moves it, saved through `move_instance` when let go, rounded to the centimetre and refused as a conflict if the file changed since the window read it. While an agent holds the file it asks "Move anyway". A left drag elsewhere, or a right or middle drag, still pans. Moving one instance of a file that leaves some unplaced saves every unplaced one where the window draws it, in the same change, so nothing jumps: this extends stage 2's "never saved" rule, flagged to the owner.
- **Out of stage 2:** changing classes, adding objects and connections, drag and drop, results views, agents setting the UI session's seed or end time, a native folder dialog, and applying each change on its own rather than reloading, which comes with the 3D view.

### Object windows (built)

## AI-native

Decided with the owner on 2026-11-07, in a grilling session. AI-native is the second design pillar, after performance (`CLAUDE.md`, ADR 0007). The model file and slice 1 of the operation catalogue (MCP v1) are built. The spec is GitHub issue 28, a sub-issue of spec issue 3, with the user stories, the order of work and the test seams.

### Decided
- **The pillar:** anything a person can do with crabsim, an AI agent can do too: build a model, run it, read the results, manage models. It's a guideline like performance, and comes second to it.
- **One operation catalogue,** in Rust, with typed inputs and outputs and descriptions, offered through front-ends (ADR 0007). The MCP server is the first front-end and the starting point. In-app agents and skills, which call the user's own LLM endpoint with the user's tokens, come second, on the same catalogue.
- **Models are readable text files,** changed only through crabsim's operations: in the UI, the user's main way, in the CLI, or through an agent's harness (ADR 0011, decided on 2026-11-08, replacing the earlier decision that agents write files with their own tools). The user controls who edits: see "Catalogue slice 2" below.
- **MCP v1:** validate a model file with precise errors, a headless run with seed, length and optional warm-up, the observations of one experiment, and each object's statistics. Live-session control comes later. Designed in detail in spec issue 37: see "Operation catalogue and MCP v1" below.
- **Where:** a standalone `crabsim-mcp` crate over stdio, a non-default workspace member, so the engine never depends on it. The server inside the UI app, so the owner can watch an agent work, comes later as another front-end.
- **No LLM inside a simulation run** by default. The owner wants AI decisions inside a run as a later opt-in that accepts its cost. The concerns are in `docs/design/ai-decisions-in-runs.md`.
- **When:** after UI stage 1. Then model as data with the file format and MCP v1, on today's objects, before build step 7. Step 7 extends the format, and each new object option comes with its operation.
- **What agents do:** everything a user does, by piloting the UI or by changing the model file: run experiments, Start and Reset, change parameters, create objects and connect them. A models folder, which the server is started with, gets list, read, write, copy and delete operations limited to it, for agents without file tools of their own.
- **Changing a model in an open UI:** after Reset or before Init, through operations, after which the run is rebuilt. The UI applies each change on its own, rather than reloading the model, because a 3D view with many detailed objects would make a full reload slow. Changing a model's structure mid-run, such as adding a Station at t = 3 days and carrying on, is an open idea and not agreed: it would be a new kind of intervention that checkpoints, replay, statistics and the Picture all have to handle.
- **Model file:** designed in detail on 2026-11-07, in `docs/design/model-file.md`, and built in three slices: slice 1 (today's objects with built-in classes, validation, canonical saving, `models/demo.json`, the CLI's `--model`) and slice 2 (derived classes, inheritance per attribute, `Model::resolve` with each value's origin) and slice 3 (`models/model-file.schema.json`, generated with `schemars` from mirror types, with drift tests against the reader, and an optional `$schema` field in files) are built. The design round also decided that a Station's process time defaults to 0 (a dummy Station), a Source's interval may be 0, and a zero-interval Source that can reach a Drain through only zero-time objects is a validation error. The file code lives in its own crate and the engine gains nothing (ADR 0009), and the CLI moved to `cli/` because of it. JSON, with a JSON Schema generated from the Rust types and published beside it, which the MCP operations reuse as their input schema. It holds the model only: objects with their configuration, names, positions and dimensions, and connections. Seed, length, warm-up and the number of observations are inputs to a run. Every object has a unique name, connections refer to names, and ids follow the file's order. 3D models will be referenced by path, never embedded, and a run never loads them. The benchmark's 429 copies need unique names.
- **Runs over MCP are jobs:** `start_run` returns an id, with `run_status`, `run_results` and `cancel_run`. Observations run on parallel threads, the first real use of distributed simulation. Results always carry their seed and crabsim's version.
- **MCP library:** `rmcp`, the official Rust SDK, pinned to `=3.9.0`, the latest on 2026-11-07, needing Rust 1.88. tokio stays in `crabsim-mcp`. The engine gains nothing (ADR 0009).
- **Skills** use the `SKILL.md` format of the Agent Skills open standard (agentskills.io), which Claude Code, GitHub Copilot, OpenAI Codex, Gemini CLI and Cursor read, each from its own folder. crabsim's own skills, such as building a model from a description or finding the bottleneck, are written alongside MCP v1, as the test that the operations are enough. The same skills work in the in-app agents.
- **LLM endpoints (phase 2):** tokens only in the operating system's credential store, never in a model file or settings file. Two API shapes: Anthropic's Messages API, and the OpenAI-compatible chat API, which also covers local models.

### Operation catalogue and MCP v1 (slice 1 built)

Decided with the owner on 2026-11-07 in a design round, and written up as [spec issue 37](https://github.com/MarcHoff94/crabsim/issues/37), which has the user stories, every decision and the test seams. The short version:

- **Crates:** `crabsim-catalogue` (default member: the engine, `crabsim-model`, `serde`, `schemars`, `rusqlite` with SQLite built in, threads, no async) and `crabsim-mcp` (not a default member: `rmcp` `=3.9.0`, tokio, stdio). The CLI becomes a second front-end on the catalogue, for people.
- **Operations:** a Rust trait with a name, a description and typed input and output that derive `schemars::JsonSchema`. `call(name, JSON)` runs one, and front-ends only translate. Structured errors (`invalid_input`, `invalid_model` with every problem, `not_found`, `outside_models_folder`, `already_exists`, `run_error`), which MCP returns as tool errors. Read-only and destructive hints over MCP.
- **Scope, the owner's concern:** crabsim's operations touch only `.json` model files in one models folder and crabsim's own `.crabsim/` there. Never crabsim's code, commands or the network. The server refuses a folder holding a `Cargo.toml`, `.git` or `.rs` file. A harness's own file tools are the harness's business.
- **Slice 1, MCP v1:**
  - `validate_model` (path or text), `list_models`, `read_model`, `write_model` (valid saved canonical, invalid saved as given with its problems), `copy_model`, `delete_model`
  - `start_run` as a job, `run_status` with simulated time reached, `cancel_run`
  - `run_results` (a short summary by default, filterable by objects and classes), `query_results` (read-only SQL, capped), `label_run`, `forget_run`
- **Runs:** observation *k* gets `splitmix64(seed + k)`. One thread per core, each running one observation, and jobs take turns for free cores. A run error fails only its observation.
- **Results store:** `<models>/.crabsim/results.sqlite`, WAL mode, with tables `runs` (including the model's canonical text and hash, label and source), `observations` and a long, thin `statistics`. Statistic names: `mus_in`, `mus_out`, `*_share`, `failures`, `availability`, `throughput_per_hour`, `mean_lead_time_s`. Mean, 95% interval, minimum and maximum over observations.
- **The CLI:** `crabsim run`, `runs`, `results` and `query` with `--models`, writing to the same store with source `cli`. Without `--models` it's unchanged.
- **People, not only agents:** the owner was clear that jobs and results are for people too. The CLI covers that until the UI's results views, which are planned in issue 37's Further Notes: a list of runs, side-by-side comparison with intervals, the model coloured by a figure, an object's figures across runs, and CSV export.
- **Recorded:** `docs/design/operation-catalogue.md`, ADR 0010 for SQLite as the results store, and the glossary words Models folder, Job and Results store.
- **Built in slice 1, and what it settled beyond the spec:** inputs carry a model as the file's text, with the model file's schema as `contentSchema`, so a harness never refuses a draft `write_model` must save. Effects are read-only, additive or destructive, and MCP's hints follow from them. Seeds are stored as text, since they use all 64 bits. The default summary leaves out objects with a blocked or failed share of 0. `cancel_run` returns once nothing of the run runs, and observations that ended keep their results. A failed observation gives no figures. `forget_run` is refused while a run is still running here, and run numbers are never reused.
- **Interrupted runs:** a run whose process ended first is marked `interrupted`, found through the lock file each catalogue holds in `.crabsim/processes/` (tables version 2). Agreed with the owner on 2026-11-07 after slice 1.
- **Known limits:** only the process that started a run can cancel it. `list_models` doesn't follow links into folders. Statistics come from what today's objects keep, so Buffers and per-MU figures wait for later.
- **Later slices of the catalogue:** 2, building and attributes, and 3, `describe_model`, the graph operations and exports, are built. Then skills, experiments and studies, and live-session operations.

### Catalogue slice 2 (built)

Decided with the owner on 2026-11-08 in a design round of six rounds, and written up as [spec issue 45](https://github.com/MarcHoff94/crabsim/issues/45) with user stories, every decision and the test seams. ADR 0011 holds the decisions that are hard to reverse. The short version:

- **`edit_model { path, changes, expected_hash? }`:** a batch of typed changes to a model file, all or nothing, checked once at the end, refused with every problem if the result is invalid. Instances, connections, classes, attributes and the model's description. `remove_class` is refused while anything depends on it unless `delete_dependents: true`. **`get_attributes`** gives every attribute with its value and origin. Files by path, no interventions yet.
- **Superseded by ADR 0013 (spec issue 73, built in its PR 1):** no edit queue, a claim with a goal and what the agent is doing, granted or refused at once, needed for every change, paused when the user takes the right. The two points below describe slice 2 as it was. `docs/design/operation-catalogue.md` describes claims as built.
- **The editor:** one per model file. Agents `claim_model` with a required purpose and wait in the edit queue, polling for now. A one-off change goes through when nobody holds or waits. An agent's right ends on release, when its process ends, or after 10 idle minutes.
- **The user controls the queue,** in the UI and the CLI, never over MCP: take the right at once, give it, choose who is next, remove, block and unblock an agent session. The user never waits and never times out. This is the AI-native pillar's first deliberate exception.
- **One person's front-end per models folder:** one UI window, holding `.crabsim/user.lock`. A second window means an independent copy of the folder. While the UI has it, the CLI can only read and run.
- **Changes from outside** crabsim, or files it has no record of, need `adopt_model` before crabsim changes them.
- **The trial's fixes:** `run_results` without per-observation values by default, `model_file_format` instead of three copies of the schema, `start_run` defaulting to seed 0 and 10 observations.
- **The CLI:** `edit`, `attributes`, `adopt` and the queue controls.

### Classes (decided, not built)
The owner wants models built in the UI later, by drag and drop, by setting values, and by deriving a class from an existing one or duplicating it and changing it. The terms are in `GLOSSARY.md`: class, instance, derived class, duplicate, inheritance. Class and instance are the words the UI uses too, because users know that much programming.
- **Derive and duplicate:** a derived class stays linked to its parent, and a duplicate is an independent copy. Classes can be derived from derived classes, and the UI and operations always show where a value comes from: built-in default, which class, or set on the instance.
- **Inheritance covers everything a user can change,** decided value by value: numbers such as a process time, and choices such as which exit strategy, once several exist. Setting a value cuts its inheritance.
- **What a derived class can change:** values only, at first. Behaviour comes later, from built-in choices such as exit strategies and from user code. A class made of several objects, as a sub-model, is its own later discussion.
- **Where classes live:** the model file holds every class it uses, so it stands alone. Shared libraries are a later discussion, with versioning as their main question.
- **A run never sees classes:** building a run works out every instance's values from its chain of classes. The per-event path is unchanged, and a headless run pays nothing.
- **Changing a class mid-run** reaches every instance whose inheritance of that value isn't cut, as an intervention at shown time. The session works out which instances that is from the model description and applies the change to each, so the run still knows nothing of classes.
- **Experiment and simulation study,** as the owner uses them: an experiment is a model with chosen values, run with a defined seed, several times with different seeds. A simulation study is several experiments of one model, each changing different values, each run a defined number of times. MCP v1 runs one experiment's runs. Studies follow, on the same job mechanism.

- **Observation** is one run of an experiment, the owner's word. "Replication" is to be avoided, and the code's `Observation`, a live session's output, was renamed `SessionOutput` as a small refactor of its own, along with `outputs()`, `OUTPUT_BACKLOG_LIMIT` and the module `observation.rs`, now `report.rs`.
- **Seeds:** an experiment has one defined seed, and its observation *k* gets a seed derived from it in a fixed way. In a study, observation *k* of every experiment uses the same seed by default (common random numbers), which can be switched off per study.
- **A study reports,** per experiment and statistic, the mean over its observations, a 95% confidence interval, and the minimum and maximum. Each observation's own figures stay available.
- **Attribute** is anything about a class or instance a user can set. Name, position and connections belong to the instance, and every other attribute, including dimensions and later the 3D model, can be inherited.
- **Interventions on instances:** setting a value on an instance cuts its inheritance, before or during a run. Restoring inheritance is its own intervention, and the instance then takes its class's current value.
- **Every attribute can change during a run, as an intervention.** That's the owner's general rule: users see attributes, never how an object works inside, and add or change behaviour only at defined hooks. A class may change an attribute during a run just as an instance may. "Reset keeps changes" applies to classes too. Today only a Station's process time can change during a run, so each attribute needs its mid-run behaviour defined when it's built. See ADR 0008, which the owner chose knowingly: watch its performance cost and reconsider it if the cost shows.
  - **Default rule:** what has already started or been scheduled keeps its values, and the change applies from the next decision on. Exceptions are decided per attribute when it's built.
  - **Refused changes:** a change that would leave the model invalid at that moment gets an error, and the value stays. For example, a capacity below the MUs held right now.
  - **Structure isn't an attribute:** instances and connections change only after Reset. The owner wants to explore mid-run structure changes later. Visual attributes change at any time, outside the intervention log.
  - **Cost:** interventions change the run directly, never as events, so the per-event path is unchanged. Each attribute's mid-run support is benchmarked as it's built.
  - **Tests:** every attribute gets one that changes it mid-run, goes back, replays and compares.
- **Attribute operations:** `set_attribute(target, attribute, value)` with an instance or class as target, `restore_inheritance(target, attribute)`, and `get_attributes(target)` with where each value comes from. Before Init or after Reset they change the model, and during a run they are interventions. Types and limits come from the Rust types and the JSON Schema, so an invalid value gets the same precise error in the file, the UI and over MCP.
- **In-app agents ask first** before writing or deleting a model file or making an intervention in the open session, with "ask every time", "allow for this session" and "always allow". Reading, validating and running are free. Over MCP the harness asks.

- **In-app agents are Markdown files** with a header (name, description, LLM endpoint and model, the operations it may call, the skills it loads, its default approvals) and its instructions below, shaped like Claude Code's subagents. Agents and skills live in the user's own crabsim folder, or beside a models folder when they belong to those models.
- **What an agent sees of a live run:** never the occurrence stream, which reaches about 1.9M occurrences per second. It reads state and statistics on request, runs until a time or a condition (such as a Drain's throughput falling below 50 per hour), and asks for recorded occurrences filtered to chosen objects and a time window.

### The model as a graph, for agents (decided)
An agent should never need to read a whole model: a model of 6,000 objects is probably 1 to 3 MB of JSON, an estimate. It retrieves only the context it needs.
- **What it can ask:** structure (neighbours, upstream and downstream within *n* steps, paths from Source to Drain, cycles), classes (the inheritance tree, which instances follow a class, where a value comes from), search by attribute, and structure joined with a study's results.
- **One source of truth:** the graph is derived from the model, kept up to date as operations change it, and read-only. Changes go through operations.
- **Graph operations in the catalogue first:** `neighbours`, `upstream`, `downstream`, `paths`, `subgraph_around`, `find_instances`, `class_tree`, computed on the model in memory, with no extra dependency. Beside them, export to standard graph formats (a Cypher script or Neo4j's CSV import, and GraphML), so anyone can load a model into their own graph database. An embedded graph database waits until the operations prove too limited, and gets its own ADR then. When this was decided the field was unsettled: Kùzu is archived, its fork RyuGraph is mostly C++, and NervusDB, in Rust, is young with a Cypher subset.
- **Results in the graph:** queries can include a study's results attached to instances, per experiment and observation. Results stay outside the model file.
- **Description:** classes and instances get an optional free-text description, visual-only, searchable and inherited, also shown in the UI.
- **`describe_model`** is an agent's entry point: instances per class, Sources and Drains, the main flows, cycles and validation problems, in a summary whose size doesn't grow with the model.

### Later, not agreed yet
- Search by meaning with embeddings (GraphRAG), if search by name, description and attribute isn't enough.
- An embedded graph database, if the graph operations prove too limited.
- Details of the in-app agent loop and LLM client.
- The MCP server inside the UI, so the owner can watch an agent work.
- Changing a model's structure during a run.
- AI decisions inside a run (`docs/design/ai-decisions-in-runs.md`).
- Shared class libraries and how they're versioned, together with a class library and explorer in the UI, with folders, deriving and duplicating there: its own design round.
- A built-in crabsim agent the user can opt in to give control of the edit queue, which knows the overall task, delegates to subagents and manages their access to the model, perhaps to parts of it. It would bring the queue's control back in line with the AI-native pillar.
- Notifying a paused agent that it can carry on, instead of it finding out on its next call (replaces notifying agents waiting in the edit queue, which ADR 0013 removes).
- An edit log of who changed what in a model file, for afterwards and for undo (out of spec 73).
- **From trial 3 (2026-11-09), not fixed by PR 77:** visual-only edits (descriptions, positions, now state notes too) change `model_hash`, so a model's last run no longer matches its file; `compare_runs` lists objects in file order, not by size of change. The missing bottleneck figure is `find_bottleneck` since PR 85.
- Running a harness such as Claude Code from inside the UI. The owner has no API key now, so agents work from an IDE. Unchecked: Claude Code's CLI runs headless as a separate program (`claude -p`) with its own login, which may not need one.
- **The security implications** of the editor right and of detecting outside changes, which the owner wants revisited (2026-11-08): both guard against accidents, not against someone determined. See issue 45's Out of Scope.
- Sub-models: classes made of several objects.

JSON is the only model file format: YAML is out.

## Known problems

- **One catalogue test fails on Linux:** `no_model_operation_reaches_outside_the_models_folder` expects `C:secret.json` to leave the models folder, which it does on Windows but which is a plain relative name on Linux, so `validate_model` answers `not_found`. The owner's PCs run Windows, where it passes; the cloud sessions of 2026-11-28 run Linux. Untouched so far: deciding whether the path check should refuse it everywhere, or the test should ask it only on Windows, is the owner's.
- **In a Linux cloud container,** the UI needs `libasound2-dev` and `libudev-dev` to build, and trying the window needs `Xvfb`, `mesa-vulkan-drivers`, `libvulkan1`, `libxkbcommon-x11-0` and `xdotool`: all installed by hand with `apt-get` on 2026-11-28, so a new container lacks them. The benchmark's wall times vary by a few percent between runs of one build there, so compare branch and `master` alternating, several times, and check instruction counts with `valgrind --tool=cachegrind`.

- **A harness runs whatever `crabsim-mcp.exe` it was pointed at,** and nothing at the root rebuilds it. On 2026-11-21 the trials in `C:\Users\marcu\projects\crabsim_trials` still ran a build from 2026-11-15, whose `model_file_format` said Buffers didn't work, so an agent optimising a model placed none. Since #131 the server compares its build's commit with its checkout's at startup and warns agents and stderr when they differ. Rebuild it with `cargo build --release -p crabsim-mcp` after pulling, with every harness using it closed, since Windows won't replace a running .exe.

- **Models without hooks are 4 to 8% slower since spec issue 156's PR 1a,** accepted for now; what was tried is under "User code (PR 1a)". samply and the Windows Performance Toolkit are installed on the first PC for the next look.
- **Models without conveyors are 2 to 4% slower since PR 135,** and no single change explains it. See "Conveyors (spec issue 133)". A profiler would settle it.
- **Illegal connections panic while running,** in a model built in code: an edge into a Source, or a self-loop. `ModelDescription` only rejects a successor on a Drain and ids not in the model. A model file can't have them: its check refuses both.

## How to work with the owner

- **Plain language and domain precision matter.** The owner knows material-flow simulation well and corrects loose models, for example that a ParallelStation is one machine rather than several. Listen for this and update `GLOSSARY.md` as terms settle.
- **Design before code.** The `grilling` and `domain-modeling` skills worked well, in rounds with recommendations where "yes" accepts. The owner often adds a requirement to a "yes", so read the whole answer.
- **Commit, push and merge only when asked.** The owner merges PRs on GitHub.
- **Test-first at agreed seams.** Behaviour tests go through `SimulationRun` in `tests/`, and session tests go through commands and observations with a fake clock.
- **Check that tests can fail.** Deliberately breaking the code keeps exposing real gaps. A same-seed replay can't detect events left over after Reset, because they land on the replay's own event times, and in step 6 this found a test that never exercised the rule it was named after. See `CLAUDE.md`.
- **Prove behaviour didn't change.** Steps 3, 4 and 6 hashed every occurrence and the final state against `master` before trusting a refactor, with a throwaway program outside the repo. Event counts alone wouldn't have shown a change in order.
- **Say what wasn't measured.** The owner reads the limits of a result, so say what a figure doesn't cover, and which ones are single runs.
- **The shell is Windows PowerShell 5.1.** `&&` doesn't work there, so give commands one per line. Git Bash is available to agents through the Bash tool.
- **Try the window yourself when asked.** With no tool for driving a desktop, a PowerShell script worked on 2026-11-13: it brings the crabsim window to the front, sends keys with `SendKeys` and clicks with `mouse_event`, moving the pointer a moment before pressing, and saves a screenshot of that window's client area to read back. It must stop on any error before sending keys and send nothing unless the crabsim window is in front, or the keys land in whatever is. Run the window on a scratch models folder, never the owner's, and close only the process you started. An agent is played by a script speaking JSON-RPC to `crabsim-mcp`.
- **Say which decisions you made while building.** The owner reads them in the PR and the summary, such as how a history entry is worded or what counts as an agent's own change.
